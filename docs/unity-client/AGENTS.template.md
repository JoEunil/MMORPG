## Coordinator 중심 운영과 착수 조건

- Coordinator(총괄)이 사용자의 유일한 일반 대화 창구다. 사용자는 각 전문 역할을 직접 지휘할 필요가 없다.
- 역할은 Coordinator·코드 구현·코드 리뷰·테스트·기획·아트·진행 문서·서버 변경 요청의 8개다. 전문 역할은 질문/제안/실패를 Coordinator에게 보고하고, 사용자에게 직접 질문하거나 다른 채팅에 메시지를 보내지 않는다. 필수 도구 권한 승인은 플랫폼 규칙을 따른다.
- 지침을 적용하고, 서버 읽기/클라이언트·문서 쓰기 경계와 Unity MCP 대상·컴파일·작은 테스트를 확인한다. 작은 기능 하나로 Coordinator 배정→구현→리뷰→실행·캡처까지 검증한 뒤 본 개발을 시작한다. 준비 문서 작성은 개발 시작이나 에이전트 실제 실행을 의미하지 않는다.
- Coordinator는 승인된 목표 안의 일상적인 구현 결정을 처리한다. 사용자는 목표/범위 변경, 미술 방향 확인, 서버 변경 승인 등 필요한 결정만 한다.
- 기본 소유권: 기획은 `BRIEF.md`, 서버 분석은 서버 계약/변경 요청 문서, 문서 담당은 `PROGRESS.md`의 기록을 맡는다. Coordinator는 작업 카드와 판단을 맡고 각 문서를 동시에 편집하지 않는다. 실제 파일은 필요할 때만 만든다.

## 서버 승인 경계 — 모든 역할에 적용

**콘텐츠 변경 범위:** 확정된 기획 범위의 서버 콘텐츠(몬스터·스킬·맵·데이터화·관련 로직)는 추가 승인 없이 구현 담당이 변경한다. 아래 승인 절차는 이 범위를 제외한 보호 영역에 적용한다. DB 스키마·인증/소유권·재화/거래 정책·새 프로토콜 계약·Zone/큐/락/풀·운영 작업과 원본 ClientCore 포괄 수정은 별도다. 콘텐츠 작업에 보호 영역 변경이 섞이면 해당 부분만 요청하고 독립 콘텐츠 작업은 계속한다. 콘텐츠 변경 허용을 임의 서비스 종료나 DB 초기화 허용으로 해석하지 않는다.

1. 일반 작업의 쓰기 범위는 `UnityClient/`, `site/`, `docs/unity-client/`, 배정된 서버 콘텐츠와 README·지침·ignore·Pages 설정이다. 보호 영역은 해당 사용자 승인이 없으면 읽기만 한다. 승인 절차를 우회해 다른 에이전트에게 변경을 대신 시키지 않는다.
2. 서버 변경이 필요하면 Coordinator가 서버 변경 요청 담당에게 분석을 배정한다. 원인, 정확한 대상 파일/동작, 최소 변경안, 호환성 영향, 테스트·복구 방법을 **`docs/unity-client/`의 문서나 patch 후보**로 준비한 뒤 Coordinator만 사용자에게 승인을 요청한다. 대상 서버 파일을 먼저 고치지 않는다.
3. 승인으로 인정되는 것은 해당 변경안에 대한 사람 사용자의 명시적 허락이다. 총괄/리뷰 에이전트의 수용, 전체 기획 동의, “데이터화하자”는 목표 선언, 테스트 실패, 침묵은 해당 서버 수정 승인이 아니다.
4. 승인은 기능/변경안 단위로 지정된 범위에만 적용한다. 해당 범위의 작은 구현·수정·검증마다 재승인받지 않는다. 대상·동작·프로토콜·DB 범위가 늘어나면 추가분을 다시 승인받는다. 승인 대기 중에는 의존하지 않는 클라이언트 작업을 진행한다.
5. 승인된 서버 변경은 Coordinator가 승인 ID·허용 파일/동작을 지정해 코드 구현 역할에 배정한다. 같은 격리된 기능 브랜치에서 클라이언트와 통합 검증할 수 있으며, 작은 변경마다 별도 체크아웃을 강제하지 않는다. DB/인증/동시성 등 독립·고위험 변경만 별도 작업을 검토한다. 서버 요청 담당은 스스로 구현자나 승인자가 되지 않는다.
6. 기존 개발 서비스를 사용하는 테스트와 서버 소스 수정은 구별한다. 서비스 시작/종료는 사용자가 정한 실행 정책만 따르고, DB 초기화·마이그레이션·계정 생성·재시딩·기존 프로세스 강제 종료를 자동 수행하지 않는다. 정상 게임 테스트로 생기는 캐릭터 상태 변경은 지정된 테스트 계정/환경에서만 허용한다.

## 구현 범위와 단순성

- 게임은 기존 서버 기능을 보여주는 3D 쿼터뷰 클라이언트다. 길드·공성전·펫 등 서버에 없는 시스템과 이를 위한 UI·더미·예비 구조를 추가하지 않는다. 콘텐츠 자율 변경도 기존 기능 범위 안에 한정한다.

- 현재 작업의 관찰 가능한 완료 조건만 구현한다. 서버에 없는 기능을 일반 MMO 관례라는 이유로 추가하지 않는다.
- ClientCore의 네트워크/ViewModel/ViewData/dispatcher 경계를 재사용한다. 원본 한 곳에서 유지하고 DLL 등 확인된 한 방식으로 Unity에 연결한다. 원본 수정은 사용자 허용 범위에서만 수행하며 별도 수정 사본을 장기 유지하지 않는다.
- 구현이 하나인 기능에 새 인터페이스·팩토리·범용 Manager·DI/EventBus/ECS 프레임워크를 추가하지 않는다. 기존 경계와 필요한 테스트 지점은 유지한다.
- 성능 근거 없는 풀링·캐싱·동시화, 예비 확장 구조, 관계없는 리팩터링을 하지 않는다. 데이터 export는 필요한 타입만 다루며 범용 코드 생성기를 만들지 않는다.
- 짧게 만들기 위해 패킷 길이 검증·오류 처리·연결 해제·이벤트 정리·메인 스레드 반영을 제거하지 않는다.
- 서버 wire format은 실제 실행 경로와 대조한다. enum 이름이나 이전 클라이언트 코드만으로 기능 지원을 단정하지 않는다.
- 서버의 수치·판정·결과를 기준으로 표시한다. 클라이언트 보간/예고와 서버 확정 상태를 구분한다.
- 새 유료 서비스·유료 에셋 구매는 사용자 허용 예산 안에서만 한다. 미확정이면 후보를 제시한다.

- 구현자는 새 추상화·전달 전용 함수·별칭 변수·중복 저장 상태에 현재 필요성이 있는지 확인하고 근거 없는 부분을 제거한다. 의미 있는 지역 변수·스냅샷·외부 경계 검증은 유지한다. 상세 기준은 `roles/implementer.md`를 따른다.
- 테스트 작성/실행 전에 작업 카드에 목표·포함/제외 범위·기대 결과·실행 비용·종료 조건을 정한다. 필요한 검증 통과 후 새 변경/실패/미해결 위험이 없으면 종료한다. 상세 기준은 `roles/unity-tester.md`를 따른다.

- Coordinator가 승인된 실행 범위 안에서 7개 전문 역할을 필요할 때 배정한다. 모두 상시 실행하지 않으며 하위 에이전트는 임의로 인원을 늘리지 않는다. 사용자 지시로 프로젝트 차원 고정 동시 인원 제한은 두지 않는다. 실행 도구 슬롯 안에서 파일·환경·의존성이 분리된 작업을 병렬화한다. 파일별 단독 소유권·Editor 단독 조작과 테스트 중 에셋 동결은 유지하며 플랫폼 상한이 변경됐다고 표현하지 않는다. 구현/테스트 파일은 한 명에게만 소유권을 준다.
- 동시에 같은 파일을 편집하지 않는다. Scene·Prefab·Material·`.meta`·패키지/프로젝트 설정은 총괄이 지정한 한 명만 수정한다. 필요한 파일만 소유하고 광범위한 재저장을 피한다.
- Unity Editor/MCP 조작 담당은 한 번에 한 명이다. 조작권은 기본 Unity 테스트 담당, 에셋 임포트/배치 때는 명시적으로 인계한다.
- 테스트가 진행 중이면 누구도 `Assets`, `Packages`, `ProjectSettings`를 수정하거나 재임포트하지 않는다. 외부 파일 수정도 자동 컴파일을 유발할 수 있다.
- 검토한 변경과 테스트한 변경이 같아야 한다. 이후 수정되면 영향을 받는 검증만 다시 수행한다.
- 테스트는 실제 관찰 결과를 확인한다. 테스트 삭제·assertion 완화·실패 은폐로 통과시키지 않는다. 미실행·차단·실패·통과를 구분한다.
- 보고는 변경 파일, 완료 조건별 근거, 실행한 검증, 남은 문제로 짧게 작성한다. 측정/실행 요약은 txt로 남기며 불필요한 JSON 결과 수집 체계를 만들지 않는다.
- 같은 원인으로 두 번 수정해도 해결되지 않으면 총괄에게 재현·시도·로그를 넘긴다. 작업 크기나 모델을 재검토하고 무한 재시도하지 않는다.
- 사용자 변경과 기존 산출물을 보존한다. 비밀번호·세션 토큰·비밀 설정은 문서/스크린샷/로그에 남기지 않는다.
- 문서 담당은 Coordinator의 확인과 실행 근거를 기록하며 승인·성공을 만들어내지 않는다. 문서 갱신 지연만으로 독립적인 개발 작업을 멈추지 않는다.
- Coordinator만 허용된 범위의 Git 통합/게시를 수행한다. 커밋·push·병합·공개 권한을 구분하고, 다른 역할은 임의로 실행하지 않는다. 기존 미완료 변경을 일괄 커밋하지 않는다.
- 공개 HTML은 검증된 내용과 선별한 미디어만 담는다. 자동 UI 테스트는 실제 입력 경로와 서버 결과를 확인하며 내부 핸들러 호출을 UI 통과로 대신하지 않는다.
- 공개 웹 작업은 PORTFOLIO_GUIDE.md의 제출 목적·실제 활용 사례·근거 있는 경험 평가·버전별 캡처·화면 확인 기준을 따른다. 원본은 SHOWCASE 개요와 작업별 MD이며 HTML은 생성 산출물이다. 생성 HTML의 본문을 별도로 편집하지 않는다.
- 에이전트 간 작업 지시는 Codex 내부에서 처리한다. Slack은 Coordinator와 지정 사용자의 요청/승인 창구로 쓴다. 요청 ID·개정·승인자 원문을 확인하며 중복 회신을 중복 실행하지 않는다. Slack 설치만으로 Coordinator 자동 재개가 가능하다고 가정하지 않는다.

## 권한 적용 시 주의

이 문서는 행동 지침이며 파일 접근을 기술적으로 차단하는 장치는 아니다. 같은 저장소에서도 쓰기 허용 폴더와 보호할 서버 경로를 명시하고 가능한 권한 제한을 적용한다. 저장소 루트 전체가 쓰기 허용된 환경을 서버 읽기 전용으로 강제한 상태라고 표현하지 않는다. 부모 세션 권한과 MCP 서버 프로세스 권한도 확인한다.
