사용자의 후속 재개 지시에 따라 기존 CAND 워크트리의 codex/client-motion-smoothing에서 서버 변경 없는 클라이언트 작업부터 진행한다. 사용자 서버 리팩토링과 독립적으로 보간·화면·기존 기능의 UI를 개선하며 서버 전환·경제/패킷 변경·새 기능 게시는 자동 재개하지 않는다. 아래 수치·계약 제안은 구현 확정이 아니다. 사용자 몬스터 AI와 A*는 작업 대상이 아니다.

## 서버 리팩토링에서 먼저 정할 접점

### 몬스터 delta 추가 점검

- 서버 dirty X/Y 작성→Broadcast→ClientCore 파싱→ViewModel dispatcher→ObservedWorld의 몬스터별 필드 병합→MotionHistory→매 프레임 Render 경로를 읽었다. 좌표가 delta에서 전혀 반영되지 않거나 Full 때마다 기존 몬스터 보간을 Reset하는 경로는 조사한 코드에서 발견하지 않았다.
- 100ms 간격 표본에75ms 표시 지연을 적용하고 끝표본 이후 hold하면, 계산상 매 주기 약25ms 동안 정지하고 다음 표본 수신 시 이미 지난 보간 구간 일부를 건너뛴다. 보간 코드가 있어도 일정 속도가 유지되지 않는 구조다. 이는 이상적100ms 입력에 대한 코드상 판단이며 사용자 세션의 실제 주원인 확정은 아니다.
- ClientCore ReceiveTick은50ms 주기로 큐를 모아 처리하고 LoginScreen.Update는 작업을 한 번에 소진한다. MotionHistory 시각은 서버 표본 시각/소켓 수신 시각이 아니라 Unity 콜백 처리 때 붙인다. 프레임 지연으로 여러 패킷이 함께 처리되면 원래 시간 간격이 압축되어 보간 속도가 튈 수 있다. 실제 묶음 발생량은 미계측이다.
- ActorMotion은 이 화면 위치의 프레임별 차이로 보행량·stride를 정하므로 위치 hold/점프가 보행에도 전달된다. 수신 파싱 누락과 표시 시간축 문제를 구분해서 후속 계측한다.
- 별도 내구성 위험: DeltaSnapshotMonster는 필드 쓰기 반환값을 검사하지 않고 dirtyBit를 지우며 Broadcast 큐 거절도 호출자에게 돌려주지 않는다. 버퍼/큐 부족이면 delta 손실 후 Full까지 기다릴 수 있다. 현재 플레이에서 이 실패가 발생했다는 근거는 없다.
- 우선 조치는 실제 간격/지터·큐 대기·표본 hold 비율을 함께 확인하고, 그 결과로 표본 시간축과 충분한 보간 버퍼를 맞추는 것이다. AI 변경이나 무조건적인 송신 빈도 증가는 선행 해결책으로 확정하지 않는다. 이번에도 코드 수정·실행 테스트는 하지 않았다.

- **시간과 이동:** 서버 틱과 몬스터 송신 주기를 구분한다. 유저 속도·몬스터 속도·시각 보정 예산을 독립적으로 유지한다. 보간 계측을 위해 표본 시각이 무엇을 뜻하는지 명시한다.
- **스킬 방향:** 월드 좌표의 각도 단위·0축·회전 방향·정규화·NaN/무한대 거절을 정한다. 요청/결과/서버 진행 중 스킬이 같은 고정 각도를 사용한다. 이동 dir 유지+aimAngle 추가와 전체 dir 전환을 비교한 뒤 패킷 길이·필드 순서·DB 영향·동시 배포 범위를 확정한다. 방향키 이동은 통상8방향이므로 float 필드만 추가해도 자유로운360도 조준 입력이 생기는 것은 아니다.
- **아이템 책임:** 수량·지급·영속성은 Cache, 현재 HP/MP·쿨다운은 Zone 캐릭터 상태다. 소비 성공 이후 회복하고 요청 ID·소유권 epoch·늦은 응답 처리를 보존한다. 퀵슬롯은 이 판정을 대체하지 않는다.
- **보상:** 처치 EXP·포션·골드를 한 보상 데이터에서 어떻게 표현할지 정한다. 지급 이벤트의 중복 방지·미로딩/실패·재접속/서버 재시작 중 보장 수준과 확정 알림을 명시한다. 기존 잔액 증가 함수 호출만으로 장애 내구성까지 보장한다고 가정하지 않는다.
- **정본 데이터:** 스킬·몬스터·성장과 같은 서버 정본→Exporter→클라 경로를 활용한다. 맵/스폰은 기존 Unity→서버 경로를 유지한다. 아이템 카탈로그 공유는 아직 추가 작업이며 이미 통일됐다고 기록하지 않는다.

## 구역 구성 제안

적은 변경을 우선하면 **Zone1 마을 유지 / Zone2 Lv1~5 / Zone3 Lv6~10 / Zone4 Lv11~15 / Zone5 Lv16~20 / Zone6 Lv21~25**를 추천한다. 이것은 추천 레벨 초안이고 성장 상한100을 낮추는 뜻이 아니다. 현재 확인한 마을 정책은 몬스터 미스폰이며 모든 피해/PvP를 차단하는 포괄 안전구역까지 구현됐다는 뜻은 아니다.

사용자가 말한 Zone1~6을 모두 Lv1~30 사냥터로 쓰려면 마을을 별도 구역으로 두거나 Zone1 안에서 마을 영역과 사냥 영역을 구분해야 한다. 기존 전체 Zone1 미스폰 정책을 변경하는 추가 범위이므로 자동 적용하지 않는다.

## 권장 진행 순서 — 서버 리팩토링 이후

1. 사용자 서버 변경과 현재 계약을 대조하고 방향/이동/보상/아이템 경계를 확정한다.
2. 몬스터 보간·모션, 유저 감속, 카메라를 한 체감 개선 묶음으로 처리한다. 그 뒤 스킬 각도·범위/VFX·밸런스를 함께 맞춘다.
3. 아이템 데이터 공유·사용 가능 표시·HP/MP와 등급·사용 슬롯·처치 골드를 하나의 소비/보상 흐름으로 연결한다.
4. Zone별 몬스터 구성·레벨·보상과 배치 밀도를 함께 조정한다. AI 리팩토링은 사용자 담당이다.
5. 거래소 결과 안내·거래 수령함을 연결한다. 무기 장착과 범용 메일은 비용 대비 범위를 따로 결정한다.

재개 시 한 번에 정할 선택: 마을/사냥터 구분, 스킬의 마지막 이동 방향 또는 별도 조준 입력, 포션 등급·공유 쿨다운, 슬롯 키, 골드 자동 지급 또는 바닥 줍기, 거래 수령함 또는 범용 메일. 지금은 답변이나 승인을 요청하지 않는다.

구현 중 작은 작업마다 검사를 만들지 않는다. 바뀐 묶음 끝에 직접 영향만 최소 검증하고 이미 통과한 검사는 반복하지 않는다. PR은 관련 사용자 기능으로 크게 묶되 서버 계약의 동시 적용 범위와 사용자 리팩토링 상태를 우선한다. 이번 정리는 검증 완료나 구현 착수 승인이 아니다.
