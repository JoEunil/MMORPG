## 2026-10-20 최신 — 조작·미술·게임 구성 개편

사용자가 초기 카툰/스타일라이즈드 방향과 클릭 이동 우선을 철회했다. 현재 목표는 리니지 계열의 정통 판타지 MMORPG 외형·UI, 방향키 이동, Z/X/C 스킬(현 서버3슬롯; V미배정), 이동·전투 속도/몬스터AI·맵·기존 성장/콘텐츠의 플레이 구성 개선이다. 텍스트 나열은 HP/MP바·아이콘·슬롯·목록 UI로 교체하되 필요한 이름/가격/수량은 유지한다. 상세 순서·완료 조건은 [개편 계획](MMORPG_REVISION_PLAN.md)을 우선하며 초기 계획의 이전 시각/입력 문구를 대체한다. 새 구현을 시작한 것으로 표시하지 않는다.

# 첫 플레이 버전 기획 초안

공통 운영·승인·병렬 실행·테스트 기준은 [현재 운영 기준](CURRENT_POLICY.md)을 따른다. 아래 역할별 규칙은 그 범위 안에서 적용한다.

목표는 **현재 서버에 구현된 기능을 보기 좋게 보여주는 3D 쿼터뷰 게임**이다. 정통 판타지, 방향키 이동·Z/X/C 스킬, 기존 몬스터·스킬·맵의 데이터화를 적용한다. 기획 담당은 이 범위 안에서 화면 흐름과 완료 조건을 작성하고 Coordinator(총괄)가 범위를 관리한다.

## 범위 제한

- 서버의 실제 처리 경로가 확인된 기능과 이를 보여주는 클라이언트 UI·아트·연출만 구현한다.
- **길드·공성전·펫 등 서버에 없는 시스템은 추가하지 않는다.** 미리보기 버튼, 더미 화면, 데이터 모델, 예비 확장 코드, 후속 구현 목록도 만들지 않는다.
- 일반 MMO 관례나 리니지라이크라는 표현은 신규 기능 추가 근거가 아니다. 퀘스트·파티·강화·자동사냥 등도 서버 구현이 확인되지 않으면 범위 밖이다.
- 콘텐츠 자율 변경은 기존 콘텐츠의 표현·데이터화·연결·필요한 로직 수정에 한정한다. 서버에 없는 시스템을 새로 만드는 권한이 아니다.
- 거래소처럼 서버 내부 구현이 있는 기능은 실제 접속 경로를 확인해 연결한다. 새로운 프로토콜·DB·인증/거래 정책이 필요한 부분은 보호 영역 승인 규칙을 따른다.

Unity 기준 버전은 사용자가 현재 사용하는 **6000.0.47f1**이다. 새 프로젝트와 패키지 호환성을 확인한 뒤 고정하며, 버전 변경이 필요한 경우 이유를 제시한다.

## 플레이와 화면 목표

로그인 → 캐릭터 선택 → 필드 진입 → 이동/몬스터 전투 → 기존 보상·상태 확인 → 다른 플레이어와 채팅 → 기존 Zone 간 이동의 흐름을 만든다. 각각의 동작은 실제 서버 처리 경로가 확인된 범위에서만 활성화한다.

첫 결과물은 한 구역의 플레이 가능한 완성 샘플이다. 화면 방향은 3D 쿼터뷰·정통 판타지로 확정했다. 고정 카메라, 읽기 쉬운 캐릭터 실루엣과 바닥 공격 예고를 기본안으로 한다. 구체적인 화면은 첫 구역 샘플로 확인한다.

리니지라이크 요소는 우선 필드에서 다른 플레이어와 함께 사냥하는 분위기, 기존 성장 정보, 스킬 단축키·채팅·인벤토리가 잘 읽히는 MMO UI로 반영한다. 거래소는 사용자가 추가한 UI/자동 테스트 목표로 포함하되 기존 내부 기능의 클라이언트 연결부터 확인한다. PK·강화·자동사냥·새 성장 규칙은 이 선호만으로 추가하지 않는다.

미술 방향은 3D 쿼터뷰 정통 판타지다. 품질은 **형태와 비례 → 실루엣과 색 구분 → 재질·텍스처 완성도 → 조명과 공간감 → 애니메이션/VFX → 추가 디테일** 순서로 높인다. 단순화를 스타일 목표로 삼지 않으며, 첫 화면 샘플에서 모델·재질·조명 조합의 완성도를 확인한 뒤 반복 제작한다. 기존 결과물이 지나치게 단순하다면 그대로 확장하지 말고 재사용 여부를 다시 검토한다.

- 조작: 방향키를 누르는 동안 서버 이동 예산에 맞춰 이동하고 떼면 멈춘다. 기존 서버 스킬 슬롯 0~2를 Z/X/C에 연결하고 V는 미배정으로 둔다. UI/채팅 입력 중 이동·스킬을 막으며 마우스는 UI·대상 선택에 사용한다. 상세 대각선·4방향 시전 규칙은 개편 계획의 계약 확인 단계에서 정한다.
- 필드: 기존 Zone 한 곳의 일부를 먼저 꾸미되 실제 좌표·경계·스폰 영역과 맞춘다.
- 캐릭터: 플레이어 외형 1종. 서버의 몬스터 유형 0/1/2에 대응하는 일반·강한 일반·보스 표현을 순차 제작한다.
- HUD: HP/MP, 서버가 제공하는 레벨/경험치, 현재 3개 스킬 슬롯, 채팅, 인벤토리. 미니맵은 기존 위치 데이터만으로 가능한 범위에서 후순위로 둔다.
- 전투 표현: 이동/대기/공격/피격/사망, 범위 예고, 타격 이펙트. 정확한 피해량처럼 서버가 제공하지 않는 정보를 임의로 확정해 표시하지 않는다.
- 미술 합격 기준: 실제 플레이 카메라에서 플레이어·적·범위 예고가 구분되고, UI가 겹치지 않으며, 재질·색·조명·아이콘 스타일이 일관된다.
- 성능 제안: 지정 PC·1920×1080에서 60 FPS 목표. 장비와 화면 내 개체 수를 정하기 전에는 합격 수치로 사용하지 않는다. Zone 최대 2,000명은 화면에 2,000명을 모두 그리라는 요구가 아니다.

경로는 기존 서버 저장소 기준이다. 주석보다 실행 코드를 우선한다.

| 기능 | 근거 | 첫 클라이언트의 처리 |
| --- | --- | --- |
| 로그인·캐릭터 목록·월드 진입 | `Login/`, `CoreLib/NonZoneHandler.cpp`, `ClientCore/ViewModel.cs` | 현재 흐름을 실제 서버에서 검증해 연결 |

화면/UI 개선은 클라이언트 작업으로 진행할 수 있다. 장비 효과, 아이템 소비, 슬롯 이동의 영속화, 자유 방향 조준, 지형 충돌 판정 등 서버 의미가 달라지는 기능은 별도 제안과 사용자 승인 전까지 구현하지 않는다. 미지원 버튼을 성공한 것처럼 동작시키지 않는다.

현재 이동 처리에서는 거리·방향·Zone 경계를 확인하지만 지형 충돌 검사는 확인되지 않았다. 처음에는 주요 이동 경로가 열린 평면 필드로 구성한다. 벽·고저차·NavMesh를 Unity에 추가하는 것만으로 서버의 이동/몬스터 AI까지 일치한다고 간주하지 않는다. 카메라 회전은 월드 방향과 입력 변환을 더 복잡하게 하므로 기본안에서는 고정한다.

## 데이터화 방향

Unity에서 작성하고 서버가 사용할 데이터만 내보내는 **빌드 시점 임베딩**을 기본 제안으로 한다. 이번 단계에서 범용 데이터 플랫폼, 실시간 핫리로드, 새 DB 테이블을 만들 필요는 없다.

```text
Unity의 타입별 데이터 에셋 + Scene의 Zone/스폰 마커
    → 내보내기 전 검증
    → UnityClient/Exports/ServerData/에 후보 데이터 생성
    → 기존 ID·계약·범위 검증 (중요한 변경은 구현·검증 후 PR 직전 최종 승인)
    → 서버용 정적 테이블에 반영하여 빌드
```

Unity 전용 Prefab·Material·Texture·애니메이션 참조는 클라이언트에만 둔다. C++ 서버에는 Mesh나 Unity Scene 파일 대신 아래 의미 데이터만 전달한다. Scene 전체나 Unity NavMesh 바이너리를 그대로 C++에 넣는 방식을 기본안으로 삼지 않는다.

| 데이터 | Unity의 작성 내용 | 서버 후보 데이터 |
| --- | --- | --- |
| 맵 | 장식, Zone 영역, 진입/연결 마커, 스폰 영역 | Zone ID·경계·기존 연결 관계·스폰 영역/유형/개체 수 |
| 몬스터 | 외형/애니메이션과 유형 ID, 기존 능력치/패턴 | HP·공격력·속도·재생성·어그로·기존 phase/skill 참조 |
| 스킬 | 이름/아이콘/VFX와 ID, 기존 phase 편집 | 마나·쿨다운·phase tick·기존 범위 타입/수치·공격력 |
| 아이템 | ID에 대응하는 이름·아이콘·설명 | 현재 서버에 있는 필드만 후보화. 장비/소비 규칙은 별도 범위 |

구현 최소안은 위 타입에 한정된 작은 Editor exporter와 명시적인 C++ 테이블 출력이다. 서버 컨테이너의 현재 형태를 최대한 유지한다. 실제 출력 형식과 연결 파일은 서버 변경 제안 때 확정한다.

데이터 계약에 필요한 항목:

1. 기존 ID 보존. 배열 인덱스로 쓰이는 skill/monster ID의 연속성·참조 유효성 확인. Unity GUID/instance ID를 서버 ID로 사용하지 않는다.
2. 좌표축·원점·단위·Zone 겹침·경계 포함 규칙과 4방향 enum을 한 곳에 정의한다. 기본안은 서버 1단위 = Unity 수평면 1단위다.
3. 시간은 실제 서버 `GAME_TICK=50ms` 기준의 정수 tick. 주석의 초 단위를 그대로 복사하지 않고 변환과 반올림 규칙을 정한다.
4. phase/step 개수, 필요한 2의 거듭제곱 조건, 스폰 수와 서버 고정 용량을 검사한다. 초기 데이터화는 현재 용량·Cell/AOI 구조를 유지한다.
5. 같은 입력이면 같은 순서·출력이 나오게 한다. 스폰은 기존 난수 생성의 영역/분포를 데이터화하며, 의도 없이 고정 좌표 스폰으로 바꾸지 않는다.
6. 콘텐츠 버전/해시를 후보 산출물과 테스트 기록에 남긴다. 현재 서버에는 새 버전 교환 프로토콜이 있다고 가정하지 않는다. 서버에 버전 노출을 추가하는 것도 승인 대상이다.
7. 콘텐츠 데이터화·로직은 P01에 따라 추가 승인 없이 진행한다. Unity 편집 수치가 자동으로 실행 서버에 적용되는 것은 아니다. 같은 콘텐츠 버전으로 클라이언트와 서버를 빌드·검증하고 실제 실행 서버 값을 동작 기준으로 삼는다.

## 기존 기능 작업 단위

아래 항목 중 확정된 기획의 몬스터·스킬·맵·데이터화·관련 콘텐츠 로직은 승인 대기 없이 진행한다. 중요한 변경이 섞이면 영향과 검증 결과를 최종 승인에 포함한다. 비가역 실행은 사전 승인을 유지한다.

기존 기능의 데이터화부터 순차 적용한다. 신규 시스템은 작업 목록에 추가하지 않는다.

- **S01 — 기존 수치 데이터화:** 스킬/몬스터의 현재 값·ID·동작을 유지하며 정적 정의를 생성 테이블로 교체. 아이템은 별도 필요가 생길 때 포함.
- **S02 — 맵/스폰 데이터화:** 현재 Zone·Cell 제약과 연결 동작을 유지하며 경계·스폰 설정을 Unity export와 연결. 변경 위치 후보는 `Cell.h`, `ZoneState_Monsters.cpp`, Zone 초기화 경로.
- **S04 — 기존 거래소의 클라이언트 연결:** 실제 네트워크 진입점 유무부터 확인한다. 없으면 요청/응답·세션/캐릭터 소유권 검증·기존 캐시 처리 연결의 최소 범위를 제안한다. 기존 거래 규칙이나 DB 스키마를 자동으로 확대하지 않는다. 후보 구현에 UI 등록/검색/구매/수령과 두 계정 테스트를 연결하고, PR 직전 최종 승인에 포함한다.

처음부터 모든 데이터를 옮기지 않는다. 기존 스킬 하나와 몬스터 유형 하나로 내보내기·참조·동일 동작을 확인한 뒤 넓힌다. 서버 승인 대기 중에는 현재 데이터에 맞춘 화면·에셋·클라이언트 테스트를 계속 진행할 수 있다.
