## 최신 사용자 지시 — 기능 묶음·검토·게시

작업 완료 뒤 별도 재개 신호를 요구하지 않고 기존 목표 안의 다음 미완료 기능을 계속한다. 관련 UI·연결·독립 리뷰·최소 검증과 공개 결과를 사용자 기능 묶음 기준 한 브랜치/PR로 모은다. 구현·리뷰·필수 검증과 로컬 커밋을 마친 뒤, PR 게시 직전에 Unity Coordinator 앱 Slack 승인을 받는다. 승인 전에는 push와 PR 생성/갱신을 보류하고 독립 작업은 계속한다. 발신은 bot token과 auth.test로 확인한 설치 앱 경로를 사용하고 사용자 계정으로 보내지 않는다. 요청에는 구체적 diff·검증·남은 위험·복구 방법과 모바일에서 답할 짧은 승인 문구를 담는다. 병합·외부 공개는 승인 범위와 확인에 따른다. 강제 종료, 데이터 삭제·초기화, 운영 조작, 비밀·권한 변경, 비용 발생 및 실행 플랫폼 통제는 별도 사전 승인을 유지한다.
## 종료 경고 분류 — 사용자 확인

정상 소켓 종료 경로의 `CancelIoEx` 실패 중 `ERROR_NOT_FOUND(1168)`은 취소할 outstanding I/O가 이미 없을 때의 비차단 진단으로 취급한다. 현재 관측된 이 경고를 미해결 기능 결함이나 다음 작업의 차단 사유로 반복 보고하지 않는다. `CancelIoEx`의 다른 오류, 다른 종료 오류, 저장/WAL 검증은 이 분류에 포함하지 않는다. 이 결정만으로 서버 로그를 지우거나 실행 가드를 전역 완화하지 않는다.
## 2026-10-19 최신 — 검증 수와 반복 최소화

작업 묶음마다 변경과 직접 관련된 최소 검증만 선택한다. 기본은 핵심 자동 시나리오 2~3개와 실제 입력 흐름 1회이며, 문구/스타일/단순 배치 변경은 영향 화면·필요 링크 확인으로 끝낼 수 있다. 자동 시험과 실입력은 각각만 확인할 수 있는 위험을 맡기고 같은 사실을 여러 방식으로 반복 증명하지 않는다. 기존 테스트 파일/기능 전체를 기본 필터로 실행하지 않는다.

범위를 넓히는 경우는 인증·네트워크·저장·공통 수명/데이터 계약을 실제로 바꿔 여러 기능에 영향이 있거나, 새 실패·미해결 위험·저장소 필수 CI가 있는 때뿐이다. 해당 직접 영향 회귀를 먼저 고르고 전체 회귀가 필요하면 이유를 한 줄 남긴다. 서버 재기동·문서 수정·캡처 추가 자체를 전체 회귀의 근거로 삼지 않는다. 이미 통과한 버전은 반복하지 않으며 수정 뒤에는 영향받은 항목만 다시 확인한다.

테스트 개수 자체를 완료 기준으로 삼지 않는다. 새 테스트는 정상 사용자 흐름과 변경이 도입한 중요한 실패 경계에 집중하고, 사소한 대입/getter·private 계산 함수 직접 호출·같은 결과의 매개변수 나열·전달 전용 단위 검사는 추가하지 않는다. 중복은 기존 시나리오의 관찰로 합친다. 필요한 수명/소유권/패킷 경계 검사를 통과 수를 줄이려는 목적으로 삭제하거나 assertion을 약화하지 않는다.

실입력은 같은 로그인에서 필요한 동작을 이어 수행한다. 같은 화면/응답을 여러 계정·재접속·패널 왕복으로 반복하는 것은 그 차이가 변경의 위험일 때만 한다. 캡처는 대표 결과 1~2장으로 제한하고 중간 상태마다 생성하지 않는다. 위험이 독립적이라 검증을 더 해야 하면 필요한 차이만 설명한다. 결과는 사용자 동작의 성공/실패와 남은 제약으로 짧게 기록한다.

## 2026-10-19 최신 — 사용자 기능 묶음과 PR

작은 구현 단계·탭·버그 수정·문서·캡처마다 PR을 만들지 않는다. 사용자가 이해할 기능 흐름이나 게임 화면 묶음 단위로 관련 UI·연결·독립 리뷰·배치 검증·공개 결과를 한 브랜치/PR에 담는다. 내부 커밋과 파일 소유권은 분리할 수 있고 서로 무관한 기능은 합치지 않는다. 제목·Slack 보고는 큰 결과, 해결한 막힘, 최종 검증만 짧게 쓴다. 기능 묶음의 구현·리뷰·최소 검증·로컬 커밋 뒤 Unity Coordinator 앱으로 승인받고, 승인 전 push/PR 생성을 보류한다. 병합·외부 공개는 승인 범위에 따라 진행한다. 되돌리기 어려운 운영·DB 파괴·비밀·권한·비용 작업과 실행 플랫폼 통제는 별도로 유지한다.
# 현재 에이전트 운영 기준

2026-10-19에 실제 개발 체크아웃 `Game-UnityClient/AGENTS.md`와 역할 지침을 확인해 반영했다. 공통 템플릿·역할·연결 문서에서 운영 기준을 참조할 때 이 문서를 사용한다. 준비·연결·승인 이력은 당시 기록이며 현재 권한을 대신하지 않는다.

## 작업 진행과 역할

- Coordinator가 작업을 배정하고 결과를 취합한다. 사용자가 전문 역할을 각각 지휘하지 않는다.
- 작업 단위가 끝나면 기존 목표와 권한 안의 다음 미완료 작업을 골라 계속한다. 단순 완료 보고 뒤 `계속`·`재개`를 요구하지 않는다.
- 사용자 결정이 필요한 요구사항, 사전 승인이 필요한 작업, 명시적 중단 요청, 전체 목표 완료 때만 멈춘다. 승인 대기 중에도 독립 작업은 계속한다.
- 전문 역할의 고정 동시 인원 제한은 없다. 실행 도구 슬롯 안에서 파일·환경·의존성이 분리된 작업을 병렬화한다. 플랫폼 슬롯 수가 늘었다고 표현하지 않는다.
- 같은 파일은 한 명만 수정한다. Unity Editor 조작권도 한 명에게만 주며 테스트 중 에셋 쓰기를 중단한다.

## 구현과 최종 승인

- 승인된 프로젝트 목표 안의 구현·수정·빌드·리뷰·로컬 테스트는 작업 브랜치에서 진행한다. 중요한 ClientCore·서버·DB 계약·프로토콜·Zone·큐·락·풀 변경도 최소 후보를 구현하고 검증한 뒤 최종 검토받는다.
- 서버 분석 담당은 원인·변경 범위·호환성·검증·복구 방법을 정리하고, 구현 담당이 후보를 만든다. 분석 담당과 리뷰 담당이 직접 구현하지 않는다.
- 기능 묶음은 구현·독립 리뷰·최소 검증·로컬 커밋 후 PR 게시 직전에 지정 Slack 스레드에서 승인받는다. 승인 전에는 push와 PR 생성/갱신을 보류한다. 변경 효과·검증·남은 위험·복구 방법을 함께 제공한다.
- 승인 대기 중에도 독립적인 작업은 계속하며, 같은 후보의 수정·재검증마다 재승인받지 않는다.
- 강제 종료, 데이터 삭제·초기화·재시딩, 운영 환경 조작, 비밀·권한 변경, 비용 발생, 외부 공개 등 되돌리기 어렵거나 기존 범위를 벗어나는 실행은 사전 승인을 유지한다.
- 지정된 로컬 테스트 서비스의 시작·정상 종료·정상 재시작과 같은 후보의 빌드 교체, 지정 테스트 계정의 정상 게임 동작은 일상 테스트에 포함된다.
- 실행 플랫폼의 파일 권한과 자동 승인 심사는 별도 통제다. 프로젝트 지침으로 이를 우회하거나 권한이 바뀌었다고 보고하지 않는다.

## 검증과 보고

- 구현 계획에서 테스트 목표·범위·기대 결과·비용·종료 조건을 정한다. 실제 기능 테스트는 작업 묶음의 구현·리뷰를 마치고 동결한 뒤 배치로 수행한다.
- 중간 컴파일 확인과 정적 검토를 전체 기능 테스트로 확대하지 않는다. 통과 후 새 변경·실패·미해결 위험이 없으면 반복하지 않는다.
- Slack 보고는 Unity Coordinator 앱으로 변경 스레드에 남긴다. 완료한 기능·문제와 해결·최종 검증·다음 작업을 짧게 쓰며 상세 로그와 식별자를 본문에 나열하지 않는다.
- 승인 요청은 필요한 근거를 준비한 뒤 `승인 <짧은 ID>`로 답할 수 있게 정리한다. 사람의 회신 원문과 대상 범위를 확인하고 중복 실행하지 않는다.
- 현재 수신기 코드는 `UnityClient/Tools/SlackReceiver/`, 발신 도구는 `UnityClient/Tools/Send-CoordinatorSlack.ps1`에 있다. 원본 `scripts/unity-client/`는 커밋하지 않는 이전 로컬 도구다.
- 수신기 대상·인증·설정·프로세스 상태는 실제 환경에서 확인한다. 코드나 문서가 있다는 사실만으로 연결·자동 재개 성공을 주장하지 않는다.

## 범위와 문서 갱신

공개 목적·콘텐츠·회고 근거·화면 이력·시각 확인·완료 기준은 사용자 작성안 기반 PORTFOLIO_GUIDE.md를 현재 원본으로 따른다. 이전 단일 소개 페이지·내부 진행 보고 방식보다 우선한다. 게시 승인·서버/DB 범위 등의 권한은 이 콘텐츠 지침으로 확대되지 않는다.

웹 결과의 최신 목적은 포트폴리오 제출용 AI 활용 개발 과정·결과물이다. 단일 AI 소개/PPT형 페이지 대신 홈·작업 목록·상세·버전별 캡처로 탐색한다. 공개 본문에서 내부 작업 ID·PR/승인/병합 상태·커밋·테스트 숫자를 제외하고 짧은 자연어 작업·문제 해결·결과와 실제 중간/개선 화면을 보여준다. 개발 묶음마다 작업별 공개 MD·현재 결과·이전 캡처 이력을 함께 갱신한다. 상세 기준은 DELIVERY.md 최신 웹 목적을 따른다.

2026-10-19 사용자는 AI-AGENT 소개 사이트 제작과 기본 github.io 주소의 첫 Pages 게시를 요청했다. Source는 GitHub Actions로 설정 완료했다. PR 전 웹 미리보기·실제 화면 확인을 제공하고, 첫 확인 뒤에는 개발 작업 묶음의 검증된 결과를 SHOWCASE → HTML → Pages에 지속 반영한다. PR은 빌드/검증/artifact까지만 수행하고, 정식 배포는 master 기준으로 한다. 병합·외부 공개 전 Slack 승인과 실제 게시 결과 확인을 유지하며 개발 완료와 웹 게시를 같은 상태로 간주하지 않는다.

기존 서버 기능을 보여주는 3D 쿼터뷰 클라이언트가 목표다. 서버에 없는 시스템이나 가짜 수치·더미 UI·예비 확장 구조를 추가하지 않는다. 원본 Game의 미완료 작업은 보존한다.

개발 체크아웃의 루트 `AGENTS.md`에서 운영 방식이 바뀌면 이 문서와 관련 역할 지침·공통 템플릿에도 함께 반영한다. 진행 이력은 `PROGRESS.md`와 `HANDOFF.md`에 두고, 재개 때 실제 파일·빌드·프로세스 상태와 대조한다.

## 브랜치와 worktree 정리

커밋만으로 브랜치나 worktree를 삭제하지 않는다. 정리는 PR이 병합됐고, 해당 브랜치를 head 또는 base로 사용하는 열린 PR이 없으며, 현재 기본 브랜치에 head 전체가 포함되고 미게시·고유 커밋이 없으며, 로컬 worktree가 현재 작업 중이 아닐 때만 한다. 일반 push에서 원격이 앞서 있거나 이력이 갈라진 것을 발견하면 중단하고 상태를 조사한다. force push, reset, 강제 삭제로 맞추지 않는다. 미게시·미병합 변경, 열린 PR, dirty worktree와 사용자 문서는 보존한다.
