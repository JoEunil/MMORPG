# AI Agent 작업에서 느낀 점과 바꾼 방식

기존 서버와 직접 만든 2D 클라이언트를 바탕으로, AI Agent에 3D Unity 클라이언트의 구현과 수정을 맡기고 실행 결과를 확인했습니다. 이 과정에서 느낀 점과 방식을 바꾼 이유를 정리했습니다.

## 원하는 결과는 구체적으로 전달해야 했다

처음에는 화면이나 동작을 말로 설명하면 의도까지 알아서 반영될 거라고 기대하기 쉬웠습니다. 실제로는 위치·크기·단축키처럼 당연하게 생각한 조건도 요구에 담아야 결과가 가까워졌습니다.

### 바꾼 방식

기능의 목표뿐 아니라 화면에서 무엇을 보고, 어떤 입력 뒤 어떤 결과를 확인할지 함께 정리했습니다. 서버가 판정하는 내용과 Unity가 보여주는 표현도 구분했습니다.

### 남은 점

세부 조건을 적는 것만으로 좋은 사용 경험이 완성되지는 않았습니다. 게임 화면에서 실제로 조작하고 피드백을 반영하는 과정이 필요했습니다.

## 자동 검증과 실제 조작감은 달랐다

자동 테스트와 입력 검증은 정해진 동작이 연결되는지 확인하는 데 도움이 됐습니다. 하지만 실시간 게임에서 느껴지는 미세한 끊김, 이동 보정의 어색함, 공격 타이밍 같은 불편은 테스트 통과만으로 찾기 어려웠습니다. 직접 플레이하며 느낀 문제를 말하고, 그 관찰을 수정과 재검증에 연결해야 했습니다.

### 바꾼 방식

동작 확인과 조작감 평가를 따로 다뤘습니다. 자동 검증은 바뀐 경로의 핵심 동작에 집중하고, 움직임이나 전투 표현처럼 사람의 체감이 중요한 변경은 실제 화면에서 확인할 항목으로 남겼습니다.

### 남은 점

실제 입력을 했다는 사실만으로 모든 끊김이나 불편을 해결했다고 볼 수는 없습니다. 무엇을 관찰했고 어떤 후보에서 확인했는지를 함께 남겨야 합니다.

## 기획·아트는 예시를 고르는 방식으로 구체화했다

기획과 아트 경험이 많지 않아 처음부터 정확한 색·배치·연출을 명세하기 어려웠습니다. 설명만 반복하기보다 같은 조건의 예시를 보고 선택하면 원하는 방향을 더 쉽게 전달할 수 있었습니다.

### 실제 선택 사례

전투·마을·사냥터·UI의 화면 시안과 전투 안내·길 진입·가방 상세의 구성안을 한 번에 비교했습니다. 사용자가 고른 조합을 이후 제작 범위에 연결했습니다. [실제 비교 시안과 선택 사례](/MMORPG/#execution-flow)

이후에는 불확실성이 큰 판단에서 대안을 만들고 장단점을 검수한 뒤, 기술 선택은 총괄이 정하고 중요한 기획·아트 방향은 사용자가 고르는 절차를 지침에 추가했습니다. 이는 대안 비교 방식이며 정식 Tree of Thought 알고리즘을 구현했다는 뜻은 아닙니다. [전체 작업 절차](/MMORPG/process/#execution-flow)

### 바꾼 방식

관련된 선택 항목을 한 보드에 모아 답변 횟수를 줄이고, 선택한 요소를 함께 제작하도록 했습니다. 선택을 기다리지 않아도 되는 독립 작업은 계속 진행했습니다.

### 남은 점

시안은 방향을 비교하는 자료입니다. 시안이 실제 게임 에셋과 화면에 그대로 구현됐다는 증거가 아니므로, 적용된 장면과 선택 기록을 구분해 보여줘야 합니다.

## 작업 묶음과 검토 기준도 조정했다

작은 단위의 PR과 반복 검증이 흐름을 끊는다는 피드백 뒤, 관련 기능을 큰 작업 묶음으로 모아 리뷰하고 이미 통과한 검증은 반복하지 않도록 조정했습니다.

리뷰 의견도 자동으로 받아들이지 않고 코드와 기존 계약에 맞는지 확인했습니다. 코드가 늘어나는 것보다 다음 수정자가 이해하고 고칠 수 있는지가 중요하다는 서버 개발 회고는 [원문](https://github.com/JoEunil/MMORPG/blob/master/AI-REFLECTION.md)에 별도로 남아 있습니다. 이 페이지는 Unity 클라이언트 작업에서 확인한 경험을 다룹니다.
