# 워크플로우 재검토와 단계별 구성 가이드

연결 준비 완료 후 Coordinator 워크플로우를 시작한다. 같은 저장소의 `master` 기준 분기와 현재 조작·미술 방향은 MMORPG_REVISION_PLAN.md를 따른다. **사용자가 서버 콘텐츠 변경의 사전 승인 생략을 허용했다.** 아래 P01의 콘텐츠 범위에 적용하며 DB/인증/기반 구조/운영 권한까지 확대하지 않는다.

## 설계 판단과 보완점

8개 역할의 책임 구분은 적절하지만 8명을 상시 실행하면 인계·비용·파일 충돌이 늘어난다. Coordinator가 고정 인원 제한 없이 도구 슬롯 내에서 필요한 독립 역할을 병렬 운용하고, 작은 작업은 구현→검토/검증으로 끝낸다. 테스트 담당은 코드 리뷰와 분리한다. UI가 보이는 것과 서버 결과가 맞는 것은 다른 검증이다.

보완할 점은 다섯 가지다.

1. 초기 ClientCore/프로토콜 연결을 저비용 구현자에게 일괄 맡기지 않는다. 최초 연결과 테스트 설계는 Sol, 명세가 고정된 반복 작업은 Luna로 배정한다.
2. ClientCore 사본을 Unity에서 별도로 계속 수정하지 않는다. 같은 저장소의 원본을 기준으로 삼는 P01 정책을 제안한다.
3. 확정된 기획 범위의 서버 콘텐츠 변경은 승인 대기 없이 진행한다. 기반 구조·DB·인증·경제 정책 변경과 서비스 재시작 권한은 구분한다.
4. Slack의 발신, 회신 읽기, 회신 후 Coordinator 재개를 각각 검증한다. 플러그인 설치만으로 양방향 자동 파이프라인이 완성됐다고 하지 않는다.
5. 공개 결과 MD를 원본으로 두고 HTML을 생성한다. MD와 HTML 설명을 두 군데서 수작업으로 관리하지 않는다.

## 빈 Unity 프로젝트 판단

**새 3D URP 프로젝트에서 시작하는 것이 적절하다.** 큰 MMO 샘플 프로젝트를 가져오는 대신, 기본 렌더러·카메라만 있는 상태에서 기존 ClientCore/서버를 연결한다. 엔진 설정까지 모두 수작업으로 만드는 완전 무템플릿 구성을 뜻하지 않는다.

- 같은 저장소의 새 worktree 안에 `UnityClient/`를 만들고 별도 `.git`를 만들지 않는다.
- Unity `6000.0.47f1`부터 호환성을 확인한다. Unity 7을 필수로 두지 않는다.
- 최초에는 URP, 입력, 필요한 UI/한글 폰트, 테스트와 Pipeline 연결만 준비한다. 대형 인벤토리 프레임워크·Addressables·멀티플레이 SDK를 미리 추가하지 않는다.
- 바닥·캡슐·고정 쿼터뷰로 로그인→이동→스킬→다른 계정 동기화부터 확인한다. 그 다음 한 구역의 미술을 완성한다.
- 현재 서버에 지형 충돌이 확인되지 않았으므로 열린 필드로 시작한다. Unity NavMesh만 추가해 서버 이동/몬스터 AI까지 해결됐다고 보지 않는다.
- 기존 C++ 서버와 ClientCore를 사용한다. Unity 플러그인에 UGS/Relay/Netcode 스킬이 있다는 이유로 서버를 해당 서비스로 교체하지 않는다.

## P01 — 콘텐츠 자율 변경과 별도 승인 경계

확정된 기획 안의 몬스터·스킬·맵·콘텐츠 데이터화와 해당 로직은 Coordinator가 배정하고 보고하며 매 기능마다 사용자 승인을 기다리지 않는다. 신규 게임 범위나 아래 보호 영역까지 승인된 것은 아니다. 원본 ClientCore의 포괄 수정 허용도 콘텐츠 변경 허용에 포함하지 않는다.

| 변경 종류 | 권장 권한 |
| --- | --- |
| Unity 화면·입력·에셋·클라이언트 코드 | 확정된 작업 범위에서 자율 구현 |
| 원본 `ClientCore/`의 Unity 호환·현 프로토콜 대응·수명/파싱 버그 수정 | 포괄 허용은 아직 미확정. 필요 변경을 Coordinator가 취합하며 원본 단일 관리 원칙 유지 |
| 기존 몬스터/스킬/맵 데이터화, 확정 기획의 콘텐츠 데이터·로직 | 추가 승인 없이 구현·로컬 빌드·비파괴 검증. 기존 ID·호환성과 서버 판정 유지. DB 스키마/새 프로토콜 계약 변경이 섞이면 그 부분만 별도 승인 |
| 거래소 등 기존 내부 기능의 클라이언트 연결 | 요청/응답·소유권 검증·재시도/중복 방지·회귀 테스트를 기능 단위 승인 후 구현 |
| 패킷 변경·영속화 의미·재화/거래 규칙·DB 스키마·인증/권한 | 신규 범위 또는 의미 변경 시 별도 승인. “콘텐츠 구현”에 포괄 포함하지 않음 |
| Zone/Cell/WorkerQueue·락·메모리 풀·AOI 구조 변경 | 콘텐츠 작업과 분리한 별도 요청. 성능 근거와 영향 검증 필요 |
| 운영 배포·운영 DB 작업·master 병합·공개 | 개발 코드 수정 허용과 별개의 권한 |

ClientCore는 현재 `netstandard2.0`, Newtonsoft.Json `13.0.3` 참조다. **원본 한 곳을 수정하고 빌드한 DLL을 Unity에 반영**하는 작은 단계를 우선 검토한다. Unity 의존성 호환성을 실제로 검사하며 DLL과 C# 사본, Newtonsoft DLL과 Unity 패키지를 중복 포함하지 않는다. 소스 commit/변경 상태와 DLL 산출물의 연결을 기록한다. 패키지화는 반복 사용의 이점이 확인될 때만 한다. 원본 ClientCore의 별도 수정 허용이 없는 상태에서는 원본을 수정하지 않는다.

승인된 클라이언트·서버 변경은 **같은 기능 브랜치의 작업 카드로 구현·통합 검증**할 수 있다. 작은 서버 변경마다 새 서버 에이전트/체크아웃을 강제하지 않는다. 위험하거나 독립적인 DB/인증/동시성 변경일 때만 별도 브랜치/작업을 나눈다. 실행할 서버는 해당 변경으로 빌드한 로컬 테스트 인스턴스여야 하며 원래 Game 폴더의 사용자 작업과 운영 인스턴스는 보존한다.

승인 요청에 로컬 재빌드·지정 서비스 재시작·전용 테스트 데이터 준비·복구 범위를 포함하면 그 안에서는 반복 승인 없이 진행한다. DB 초기화나 기존 플레이어 데이터 변경을 테스트 준비에 암묵적으로 포함하지 않는다.

## 에이전트 간 작업 지시

**에이전트끼리 Slack을 연결할 필요가 없다.** Coordinator가 Codex 하위 에이전트에 작업 카드를 전달하고, 결과를 받아 다음 담당자에게 인계한다. 공통 상태는 저장소 문서와 실제 변경/검증 결과에 둔다. 역할별 Slack 봇이나 8개의 사용자 채팅은 만들지 않는다.

```text
사용자 ↔ Slack의 Coordinator 승인/확인 스레드
             ↕ 읽기·발신 및 승인 후 재개 연결
          로컬 Codex Coordinator
             ├─ 기획 / 서버 계약 분석 → 필요한 승인 요청
             ├─ 구현 / 아트 → 고정된 변경
             ├─ 리뷰 + 테스트 → 통과 또는 수정 인계
             └─ 문서 → 공개 MD → HTML → Pages
```

실제 인계는 작업 생성/메시지/결과 대기 기능으로 처리한다. 완료 조건, 기준 commit, 수정 파일, 금지 범위, 테스트, 승인 ID를 전달하며 전체 대화를 매번 복제하지 않는다. 같은 기능을 이어갈 때는 기존 역할 작업을 재사용하고 불필요한 재생성을 줄인다. 실행 환경의 동시 한도 안에서 필요한 역할만 활성화한다.

테스트 실행 동안 관련 코드·에셋·서버 빌드 변경을 멈춘다. 고정된 diff의 리뷰는 실행 테스트와 병행할 수 있다. 수정이 생기면 영향을 받는 검증을 다시 한다. 하위 에이전트는 부모의 권한/MCP를 상속하며 모델·지침만으로 서버 쓰기 제한이 기술적으로 생기지는 않는다.

## Slack 승인과 자동 재개

사용자 의도는 변경 요청과 직접 확인할 사항을 Slack에서 처리하는 것이다. **Coordinator만 지정 채널에 요청·완료·차단 사항을 올리는 방식**을 기본으로 한다. 

1. 사용할 워크스페이스·채널 ID, 승인할 사용자 ID, 공유할 자료 범위를 정한다. 필요하면 비공개 프로젝트 채널을 사용한다.
2. Slack 연결의 메시지 발신·스레드 회신 읽기·첨부 자료 기능을 실제로 확인한다. 설치 여부와 작동 여부를 구분한다.
3. 요청마다 `REQ-번호 / 개정번호`, 이유, 수정 파일/동작, 검증·복구, 영향을 한 메시지로 올린다. 미술 확인은 캡처와 선택지를 붙인다. 로컬 파일 경로는 다른 기기에서 열리지 않으므로 허용된 첨부/접근 가능한 링크를 쓴다.
4. 현재 최소 수신기는 [MCP_SETUP.md](MCP_SETUP.md)의 전용 스레드 하나를 사용한다. 요청도 그 스레드에 올리고 사용자는 `!coord REQ-번호 r1 승인`, `!coord REQ-번호 r1 거절`, `!coord 수정 요청: ...`처럼 답한다. 인증된 승인자 ID·채널·스레드·요청 개정과 원문 링크/시각을 기록한다. 다른 사람/봇/인용문·애매한 이모지·무응답을 승인으로 처리하지 않는다.
5. 승인 범위가 바뀌면 새 개정으로 요청한다. 같은 범위 내 구현 보완은 기존 승인을 유지한다. 중복 이벤트로 두 번 실행하지 않는다.
6. **회신 수신과 Coordinator 재개를 한 번 왕복 시험한다.** 연결이 자동 수신/재개를 제공하지 않으면 설치만으로 무인 승인이 가능하다고 하지 않는다.

자동 재개가 꼭 필요한데 기존 연결에 해당 기능이 없으면, **작은 로컬 Slack 수신기 하나**를 추가하는 방안을 검토한다. Slack Socket Mode/Bolt로 승인 이벤트를 받고, 지정된 로컬 Codex 작업을 지원되는 방식으로 재개한다. 공개 수신 서버 없이 연결할 수 있지만 PC와 수신기가 켜져 있어야 한다. [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)

현재 설치된 Codex CLI의 `codex queue --thread <명시적인 채팅 ID> --message <내용>`으로 기존 준비 채팅이 실제 재개되는 것을 검증했다. 대상 ID를 고정하고 `--last`로 다른 작업을 선택하지 않는다. Desktop 작업을 별도 실행기로 복제하지 않는다. 연결 대상과 검증 근거는 [MCP_SETUP.md](MCP_SETUP.md)에 기록한다.

수신기는 승인 사실만 검증해 전달하며 Slack 메시지를 셸 명령으로 실행하지 않는다. 토큰은 로컬 비밀 저장소/환경에 두고 저장소에 넣지 않는다. 요청/개정/처리 상태를 최소한으로 보관해 재시작·중복 수신에 대응한다. 일반 대화 수집·역할별 봇·별도 작업 DB부터 만들지 않는다. 필수 도구/OS 권한 승인은 Slack의 업무 승인과 별개이며 우회하지 않는다.

## Coordinator 시작 전 연결 준비와 시작 후 개발

연결 준비는 사용자와 현재 준비 담당이 끝낸다. Coordinator와 전문 에이전트를 먼저 실행시키지 않는다. 같은 저장소의 작업 공간과 빈 Unity 프로젝트는 연결 대상이므로 이 준비 단계에서 만들 수 있다.

1. 전용 worktree/브랜치와 빈 URP 프로젝트를 준비하고 기본 컴파일 확인.
2. Unity CLI·Pipeline·MCP를 연결하고 대상 경로·Scene 읽기·Play/Stop·PNG 확인.
3. 작은 임시 테스트 Scene에서 가상 마우스 클릭/키 입력→화면 변화→assertion 검증. 실제 게임 이동/스킬 검증은 기능 구현 후 진행.
4. Unity Recorder를 설치해 Editor Play Mode에서 짧은 GIF 1개 저장·재생 확인. 독립 실행 파일 녹화와 구분.
5. Slack 지정 채널·승인자와 발송/회신/동일 Coordinator 실행 재개 방식을 시험.
6. 테스트 서비스 경로·재시작/데이터 준비 권한을 정하고 게임 계정 2개로 로그인을 확인. 게임 UI/ClientCore 통합은 개발 단계에서 확인.
7. 연결된 도구·버전·프로젝트·성공/미검증 항목을 짧게 인계하고, 사용자가 워크플로우 시작을 지시할 때 Coordinator를 시작한다. 자동 커밋/push/병합/게시 미확정 권한은 실행하지 않는다.

CLI는 명령 전달 방식이며 GUI 실행을 배제하지 않는다. Editor Play는 MCP/CLI로 제어할 수 있다. 빌드된 클라이언트 실행은 빌드/프로세스 실행 단계이고, 그 Player의 내부 조회·입력 제어에는 해당 빌드의 별도 테스트 연결이 필요하다. 임의의 EXE를 MCP가 자동 조작한다고 보지 않는다.

입력은 Input System의 가상 Mouse/Keyboard로 실제 입력 처리→UI/게임 로직→서버 응답을 확인하는 PlayMode 테스트를 우선한다. 직접 이동 함수를 호출하거나 패킷만 보내는 테스트는 UI 입력 검증으로 표시하지 않는다. 이 방식은 OS 포커스·실제 장치를 검증하지 않는다. 해당 검증은 별도 입력 자동화가 연결된 경우에만 수행한다.

녹화는 GPT 플러그인 대신 Unity 패키지 `com.unity.recorder`로 구성할 수 있다. Editor Play Mode의 영상/GIF를 지원하지만 standalone Player 녹화는 지원하지 않는다. 짧은 Recorder API 호출로 자동화하고 별도 녹화 프레임워크를 만들지 않는다. [Unity Recorder](https://docs.unity3d.com/Packages/com.unity.recorder@5.1/manual/index.html), [Input System 테스트](https://docs.unity3d.com/ja/Packages/com.unity.inputsystem@1.4/manual/Testing.html), [CLI 실행 안내](https://docs.unity.com/en-us/unity-cli/release-notes)

테스트 계정은 DB 관리자 계정이 아니라 게임 로그인 계정 2개다. 현재 `Login/routes/auth.js`의 `/signup` 라우트는 비밀번호를 해시해 `users`에 저장한다. 실제 URL prefix와 테스트 DB 연결을 확인한 후 기존 회원가입 경로를 사용하고, 로그인·캐릭터 준비도 확인한다. 계정 생성은 지정된 테스트 DB와 허용된 데이터 준비 범위에서 수행한다.

## 전체 순서 참고

| 순서 | 작업 | 통과 기준 |
| --- | --- | --- |
| 1 | 범위·P01·자동 커밋/push/병합/공개 범위 확인 | 승인된 범위와 아직 미승인인 범위를 기록 |
| 2 | master 기준 전용 worktree/브랜치 준비 | 기준 commit 확인, 기존 미완료 변경 보존 |
| 3 | 빈 3D URP UnityClient 프로젝트 생성 | Editor/패키지 버전 고정, 빈 프로젝트 컴파일 성공 |
| 4 | 공통/역할 지침과 모델 설정 적용 | 시작 모델·추론·동시 한도 확인. 이 문서만으로 설정됐다고 하지 않음 |
| 5 | Unity CLI·Pipeline·MCP 연결 | 정확한 프로젝트, 도구 목록, 생성/저장/컴파일/테스트/캡처 성공 |
| 6 | Slack 연결과 승인 왕복 검증 | 요청→본인 회신→정확한 요청 승인 기록→같은 Coordinator 작업 재개. 중복 수신 시 재실행 없음 |
| 7 | 테스트 서버와 ClientCore 연결 | 지정 계정 로그인·Zone 진입, 서버 소스/실행 빌드 일치 |
| 8 | 작은 기능의 전체 에이전트 흐름 검증 | Coordinator→구현→독립 리뷰/실행 테스트→txt·PNG→문서, 실패 수정도 한 번 확인 |
| 9 | 첫 플레이 구역 완성 | 클릭 이동·스킬·두 계정 동기화와 화면 샘플 사용자 확인 |
| 10 | 승인된 콘텐츠/데이터화·거래소 확장 | 실제 서버 결과·재접속/중복 요청 회귀, 대표 GIF |
| 11 | 결과 MD→HTML·Pages | 공개 내용 확인, 배포 URL 검증, README 연결 |

5번/6번 연결 준비는 독립적으로 진행할 수 있다. 첫 미술 샘플은 7~9번과 병행하되 동일 Scene/Editor 조작은 순서대로 한다. 거래소·데이터 스키마의 서버 변경 필요성은 초기에 분석해서 승인 대기를 늦추지 않는다.

공개 문서 원본은 필요할 때 만드는 `docs/unity-client/SHOWCASE.md` 하나로 시작한다. 기획/내부 승인 기록/전체 로그를 통째로 변환하지 않고, 검증한 결과와 대표 자료만 담는다. 작은 HTML 템플릿과 변환 단계로 `site/` 산출물을 생성하고 Pages에 게시한다. 원본 MD·스타일·미디어가 바뀌면 다시 생성하며 생성 HTML의 본문을 직접 수정하지 않는다. 상세 기준은 [DELIVERY.md](DELIVERY.md)를 따른다.

## 시작 전에 사용자에게 받을 값

- 콘텐츠 변경 자율 진행은 확정. 보호 영역에 해당하는 변경과 원본 ClientCore 허용 범위만 필요시 확인.
- Slack 워크스페이스·채널·승인자, 알림/자료 공유 범위. 토큰을 대화에 붙이지 않는다.
- 테스트 계정 2개, 서버 실행 경로/버전, 서비스 시작·재시작과 전용 데이터 준비 범위.
- 자동 커밋/push/병합/공개 범위. 스킬 키·카메라·미술 세부는 첫 샘플에서 확정할 수 있다.

새로운 대형 설계 문서나 역할을 추가하기보다 위 연결·승인·첫 플레이 흐름을 실제로 검증하는 것을 다음 목표로 삼는다.
