# 다음 준비 — 내 아이템 매물 등록

2026-10-20 코드 읽기만 수행. 제품 코드·DB·빌드·게임·Git은 변경하거나 실행하지 않았다. 이 문서는 구현 승인이나 구현 착수를 뜻하지 않는다.

## 현재 계약

- 외부 네트워크에는 등록 요청이 없다. `CoreLib/PacketTypes.h`는 opcode 37까지고 `BAZAAR_REGISTER`/응답은 없다. 내부 `MSG_BAZAAR_REGISTER`만 `CacheLib/Handler.cpp`가 처리한다. ClientCore에도 등록 API가 없다.
- `CacheLib/Config.h::QUERY_13`은 매물 테이블에 `TRADING` 행을 바로 INSERT하는 SQL이며 저장 프로시저가 아니다. `Handler_Bazaar.cpp`는 파라미터 `(itemID, sellerID, itemType, quantity, price)`로 이를 실행한다.
- 품목·종류는 `CoreLib/ItemData.h`의 ID 1–5에서 확인한다. 핸들러는 존재하는 ID와 양수 수량만 검증하고, 클라이언트 price의 0/수수료 범위는 검증하지 않는다. 수수료는 `max(10, price / 10)`으로 차감한다. 이 계산과 기존 규칙은 바꾸지 않는다.
- 등록은 먼저 `PartialUpdate`로 인벤토리에서 수량을 빼고, 이어 `TryWithdrawCurrency`로 gold를 빼고, 마지막에 비동기 INSERT를 한다. 두 cache 변경은 한 트랜잭션이 아니며 각각 나중에 flush된다. 앞 단계가 실패하면 보상용 `PartialUpdate`/`DepositCurrency`를 호출하지만 실패 시 로그만 남긴다.
- INSERT가 1행이면 status 1, 자원 부족은 2/3, 잘못된 item은 4, insert/큐 실패는 status 0을 반환한다. SQL 예외는 insert 실패처럼 취급해 아이템과 gold를 돌려준다. DB worker의 다른 예외 경로는 메시지만 반환하고 보상·응답을 하지 않는다.

## 안전성 판단

TCP/UI만 연결하는 안전한 후보는 현재 없다. INSERT가 서버에 반영된 뒤 응답을 잃으면 handler가 실패로 판단해 cache 아이템과 수수료를 보상할 수 있어, 매물과 원래 자원이 함께 남을 가능성이 있다. 반대로 worker 예외 경로에서는 자원을 차감한 채 응답과 매물이 없을 수 있다. 외부 requestID를 추가해도 DB가 이를 기록하지 않으므로 재시도 중복이나 결과 판별을 막지 못한다. 동일한 판매자·품목·수량·가격의 기존 매물 조회도 별개의 정상 매물과 불명확한 요청을 구분하지 못한다.

매물 등록을 노출하기 전에는 등록의 중복 억제 키와 최종 상태를 DB에서 조회할 수 있는 최소 영속 계약이 필요하다. 이는 현재 스키마에 없는 계약이므로 별도 서버 분석·승인 범위로 다룬다. 새 수수료나 경제 규칙은 추가할 이유가 없으며 기존 수수료만 보존해야 한다. 영속 식별·보상 결과까지 보장할 수 없으면 취소·구매처럼 UI만 연결하지 않는다.

## 가장 작은 후속 후보와 데이터 한계

안전 계약이 마련된 뒤에만 기존 거래소 안에 **가방 아이템 선택 → 수량·판매가 입력 → 수수료 표시 및 확인 → 결과 표시 → 가방/내 매물 갱신**을 연결한다. 확인 전 item 수량·수수료를 추정해 성공 상태로 보이지 않는다. 성공 결과가 애매하면 자동 재등록이나 클라이언트 보상 없이 상태 조회를 안내한다.

최근 실제 UI에서는 내 매물이 비어 취소가 비활성인 것을 확인했다. 전용 계정의 이전 READ ONLY 점검에서도 캐릭터 5011/5012 인벤토리 행이 비어 있었다. 이번에는 최신 인벤토리·gold 잔액을 조회하지 않았으므로 실제 등록 자원 부족이라고 단정하지 않는다. 등록 성공·수수료 차감은 미검증이며 임의 아이템/gold 지급, DB seed, 다른 계정 사용은 검증 방법으로 삼지 않는다.

## 구현 전 보완과 최소 검증

먼저 서버 분석으로 DB 중복 억제·불명 결과 재조회·보상 원자성의 구체 계약과 복구 방법을 정하고, 독립 리뷰가 가능한 최소 후보를 확정한다. 단순 외부 requestID 전달이나 timeout UI만으로 이 위험을 닫았다고 처리하지 않는다.

후보 확정 후에는 자동검증을 두 경계로 제한한다: (1) 인증된 field character·wire 상관관계·DB 재시도/중복 등록, (2) 확인/취소·수량/수수료·실패 및 불명 결과 표시. 실제 입력은 본인 인벤토리와 gold를 먼저 READ ONLY로 확인하고, 기존 게임 경로의 재료만 있을 때 한 번의 등록 흐름으로 검증한다. 자원이 없으면 UI 비활성·실패 결과까지만 확인하고 등록 성공을 주장하지 않는다.
