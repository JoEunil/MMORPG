## 원격 브랜치 자동 삭제 — 사용자 설정 확인

2026-10-20 사용자가 GitHub의 Automatically delete head branches 설정을 적용했다고 알렸다. PR 병합 후 원격 작업 브랜치는 이 자동 삭제를 기본으로 사용하고 실제 삭제 여부를 확인한다. 남아 있을 때만 기존 안전 조건을 확인해 수동 정리한다. 로컬 브랜치와 worktree는 자동 삭제 대상이 아니므로 fetch --prune 후 미게시·고유 커밋과 사용 여부를 별도로 확인한다. 커밋 완료만으로 삭제하지 않으며, 자동 삭제를 위해 브랜치를 강제 변경하거나 보호 설정을 완화하지 않는다.

## 2026-10-20 브랜치 수명과 이력 보존

커밋만으로 삭제하지 않는다. PR 병합과 현재 기본 브랜치에 작업 전체가 포함된 것을 확인한 뒤 작업 브랜치를 정리한다. 미게시·고유 커밋, 열린 PR, 진행 중인 작업, 사용 중인 worktree와 사용자 변경은 보존한다. 원격 삭제 후 로컬 브랜치도 별도로 확인한다. push 전 fetch와 이력 분기 확인을 수행하고, 충돌/분기가 있으면 병합해 보존한다. 승인 없이 reset·강제 push로 원격 이력을 교체하지 않는다.

## 최신 사용자 지시 — PR 게시 직전 Slack 승인

작업 완료 뒤 별도 재개 신호를 요구하지 않고 다음 미완료 기능을 계속한다. 테스트는 기능 묶음 완성·리뷰 후 직접 영향 최소 항목만 실행한다. PR은 관련 변경을 큰 단위로 모으고, 구체적 diff·검증·남은 제한을 준비한 게시 직전에 Unity Coordinator 앱으로 Slack 승인을 요청한다. 사람 원문 승인 전 push·PR 생성은 보류하며 로컬 구현·커밋과 독립 작업은 계속한다. 이전의 '먼저 PR 생성' 허용보다 이 최신 지시가 우선한다. 보호 영역의 기존 승인 경계와 플랫폼 통제는 그대로 적용한다.
## 2026-10-19 최신 — 사용자 기능 묶음과 PR

작은 구현 단계·탭·버그 수정·문서·캡처마다 PR을 만들지 않는다. 사용자가 이해할 사용자 기능 흐름이나 게임 화면 묶음을 기준으로 관련 UI·서버/클라이언트 연결·독립 리뷰·배치 검증·공개 사이트 결과를 한 브랜치/한 PR에 담는다. 내부 커밋과 파일 소유권은 분리할 수 있다. 서로 무관한 기능을 크기만 키우려고 섞지는 않는다. 제목·Slack 보고는 큰 결과, 막힌 점의 해결, 최종 검증만 짧게 쓴다. 사용자가 PR을 먼저 올리면 검토·승인한다고 지정했으므로 검토 가능한 검증 묶음의 일반 push/PR 생성은 진행하고 병합·공개는 승인 전까지 기다린다. 되돌리기 어려운 운영·DB 파괴·비밀·권한·비용의 기존 사전 승인과 실행 플랫폼 통제는 유지한다.

## 최신 웹 목적 — 포트폴리오 제출용 과정과 결과물

목적·콘텐츠·회고 근거·화면 이력·대표 화면/갤러리 선확인·완료 기준의 상세 원본은 [공개 웹 포트폴리오 지침](PORTFOLIO_GUIDE.md)이다. 사용자 작성안을 반영한 이 지침을 사이트 관련 역할이 함께 따른다. 아래 요약이 이전 문구와 충돌하면 PORTFOLIO_GUIDE를 우선한다.

2026-10-19 사용자 보정: 웹사이트는 AI 활용 개발의 과정과 결과물을 제출용으로 보여주는 포트폴리오다. 에이전트 소개만 있는 한 페이지나 내부 진행 보고서가 아니다. 첫 초안은 배포 테스트용으로 먼저 게시하고 이후 전면 개편한다. 아래의 이전 단일 소개 페이지 문구보다 이 기준이 우선한다.

- 홈은 실제 결과물과 짧은 프로젝트 설명을 먼저 보여준다. 작업 목록·작업 상세·캡처 이력은 링크로 둘러보는 여러 페이지로 구성한다.

- C08/C09 같은 내부 ID, PR/승인/병합 상태, 커밋 해시·테스트 개수는 공개 본문에 노출하지 않는다. 근거는 필요한 저장소 링크로 분리하며 내부 운영 기록은 비공개 증거 문서에 남긴다.
- 실제 캡처를 중심으로 작업/화면 버전을 명확히 연결하고 이전 캡처를 보존한다. 최신 결과와 이전 모습을 비교할 수 있게 한다. 지금의 거래소 숫자 텍스트 UI는 완성형 UI가 아닌 중간 결과물로 설명하며 이후 실제 UI 개선 결과로 갱신한다.

- 첫 웹 확인 이후 개발 묶음 완료 시 작업 상세·현재 결과·선별한 버전별 캡처를 함께 갱신한다. 게시 전 링크 탐색·모바일·이미지/캡션·내부 문구 비노출을 확인한다. 게임 시험을 사이트 갱신 때문에 반복하지 않는다.

같은 Game 저장소, `master` 기준 분기는 사용자 확정 사항이다. 아래 폴더·게시·자동 커밋 정책을 실행 전에 적용한다.

## 작업 경계와 Git

확정 권한: 개발 시작 후 관련 검증을 통과한 작업만 codex/unity-ai-client에 커밋할 수 있다. push·병합·공개는 별도 승인이다. 준비 단계에서는 커밋하지 않는다. 상세 권한은 LOCAL_PREPARATION.md를 따른다.

- 기준: 착수 시 원격 상태를 확인하고 사용할 `master` commit을 기록한다. 기본 브랜치를 임의로 바꾸지 않는다.
- 전용 브랜치 이름 제안: `codex/unity-ai-client`. 기존 Game 작업 폴더의 변경을 보존하기 위해 같은 저장소의 별도 worktree를 사용한다. 별도 저장소나 서브모듈은 필요 없다.
- 새 worktree에는 기존 미커밋 변경이 자동으로 따라오지 않는다. 이 준비 문서는 필요한 파일만 가져오고, 서버 변경 전체를 함께 복사하거나 커밋하지 않는다. 추가 서버 commit이 필요하면 Coordinator가 기준 변경을 확인한다.
- Coordinator만 통합 커밋/push를 담당한다. 파일별 변경을 확인하고 작업 범위만 stage한다. 전체 파일 일괄 추가, 사용자 변경의 무단 포함, 강제 push와 기존 작업 초기화를 하지 않는다.
- **자동 커밋·push·병합·공개는 서로 다른 결정이다.** 실행 전 허용 범위를 한 번 기록하고 그 안에서는 반복 승인 없이 진행한다. 권장안은 리뷰/관련 테스트 후 작업 브랜치 자동 커밋, 기본 브랜치 병합과 첫 공개는 사용자 결정이다. 미확정 상태를 자동 실행 허락으로 간주하지 않는다.

| 위치 | 내용과 기본 쓰기 범위 |
| --- | --- |
| `UnityClient/` | Unity 프로젝트와 ClientCore 참조 산출물, 클라이언트 테스트, 서버 export 후보 |
| `docs/unity-client/` | 기획·역할 지침·진행 기록·서버 변경 요청 |
| `site/` | 공개할 HTML/CSS와 선별한 화면 자료 |
| 저장소 루트의 README·AGENTS·`.gitignore`, 지정 Pages workflow | 해당 클라이언트/소개 작업에 필요한 변경만 |
| 기존 서버 코드·프로토콜·DB·설정·원본 ClientCore | 승인 없는 범위는 읽기 전용. P01 콘텐츠 범위는 자율 변경, 그 외는 개별 승인표와 작업 카드 적용 |

같은 저장소라는 이유로 서버 수정까지 허용되지 않는다. `AGENTS.md`는 행동 규칙이다. 실제 파일 권한과 MCP 프로세스 권한도 별도로 확인한다.

ClientCore 단일 원본 관리와 콘텐츠 자율 변경과 보호 영역 승인을 나누는 P01 정책은 [PIPELINE_GUIDE.md](PIPELINE_GUIDE.md)에 있다. 승인된 작은 서버 변경은 같은 기능 브랜치에서 통합 검증할 수 있다.

## HTML 소개와 GitHub Pages

공개 페이지는 **AI 에이전트로 무엇을 어떻게 만들었고 실제로 어디까지 검증했는지** 설명한다. Unity 실행 파일이나 WebGL 빌드를 호스팅하는 작업은 포함하지 않는다.

공개 내용 원본은 `docs/unity-client/SHOWCASE.md` 하나로 시작한다. 같은 문서 폴더의 작은 HTML 템플릿과 변환 단계로 `site/index.html`을 생성하고 `site/style.css`, `site/media/`와 함께 게시한다. 목표, 8개 역할과 인계 흐름, 구현 기능, GIF/캡처, 테스트 결과·제약, 소스 링크를 담는다. 생성 HTML 본문을 직접 고치지 않는다. 결과가 늘면 필요한 부분만 나누고 별도 웹 프레임워크·문서 DB·실시간 대시보드는 만들지 않는다.

- 아트는 색·레이아웃·대표 이미지 방향, 구현은 HTML 템플릿/CSS·작은 변환 단계·접근성·반응형 표시를 맡는다. 문서 담당은 공개 MD의 설명·상태·캡션을 갱신한다. Coordinator가 실제 검증 근거와 공개 범위를 확인한다.
- 내부 역할 지침과 전체 로그를 그대로 공개하지 않는다. 계획/구현 완료/실행 검증을 구분하고, 캡처에는 시나리오·대상 commit을 붙인다.
- 소개 페이지의 기록 갱신이 불필요한 코드 변경이나 전체 테스트 재실행을 유발하지 않게 한다. 공개용 사진 몇 장을 위해 모든 테스트를 매번 녹화하지 않는다.

## 공개 설명과 이미지 구성

HTML 전담 에이전트는 추가하지 않는다. Coordinator는 첫 플레이 구역 완성, 주요 기능 묶음 검증 완료, 사용자 공개 요청 때 사이트 갱신 작업을 기존 구현 담당에게 배정한다. 작은 코드 변경이나 매 대화마다 HTML을 다시 만들지 않는다. 최초에 구현 담당이 템플릿·변환·미디어 배치를 만들고, 이후에는 같은 변환 절차를 재사용한다. 아트는 필요할 때 시각 구성을 지원한다.

문서 담당의 MD 인계는 공개 페이지 완료가 아니다. 공개 작업은 `MD·미디어 선정 → 구현 담당의 HTML 생성·배치 → 브라우저 확인 → Coordinator의 허용 범위 내 게시`까지 추적한다. 게시 권한이 없으면 로컬 HTML 미리보기와 검증 결과까지 완료하고 게시만 대기로 남긴다.

웹 페이지는 결과 목록뿐 아니라 프로젝트 목적, 에이전트 역할·작업 흐름, 연결 구성, 구현 과정의 주요 결정과 실제 결과를 정리한다. 내부 지침은 공개 독자가 이해할 설명으로 요약한다. Markdown 원본을 그대로 나열한 화면으로 끝내지 않는다.

- 문서 담당이 내용에 맞는 대표 캡처·GIF와 설명 도식을 선정하고 본문 위치·캡션·대체 텍스트를 함께 정한다. 부족한 자료는 Coordinator를 통해 테스트/아트 담당에게 요청한다. 사용자가 이미지를 하나씩 지정하거나 붙이기를 기다리지 않는다.
- 첫 화면은 실제 게임 대표 화면과 짧은 소개에 집중한다. 활용 과정은 역할/인계 나열 대신 사람의 판단·에이전트 작업·검토와 수정이 드러나는 실제 사례로 설명하고, 작업 상세에는 결과 화면과 짧은 관찰을 연결한다. 실제 자료가 없으면 해당 영역을 생략하며 완료된 화면처럼 꾸미지 않는다.
- 실제 캡처를 기능 구현·검증 증거로 사용한다. 생성 일러스트나 콘셉트는 필요할 때만 보조 자료로 쓰고 명확히 표시한다. 설명과 관계없는 장식 이미지를 양산하지 않는다.
- 아트 담당은 이미지 선택·크롭·색감·일관된 배치를 지원하고 구현 담당은 반응형 HTML/CSS로 적용한다. 캡처의 오류나 UI를 지워 기능이 정상인 것처럼 보이게 하지 않는다.
- 이미지는 읽을 수 있는 크기로 압축하고 가로세로 비율을 유지한다. 긴 GIF는 필요한 경우 짧은 영상과 미리보기 이미지로 대체한다. 글자·HUD가 읽히는지, 모바일에서 잘리거나 넘치지 않는지 확인한다.
- 이미지/미디어는 상대 경로로 연결하고 GitHub Pages의 저장소 하위 경로에서도 표시되는지 확인한다. 출처·사용 조건을 확인한 자료만 공개한다.
- 게시 전 실제 HTML을 브라우저로 열어 데스크톱/모바일 너비, 이미지 누락, 도식 가독성, 영상/GIF 재생, 캡션·링크를 확인한다. 페이지 생성 성공만으로 완료 처리하지 않는다.

게시 기본안:

1. 저장소 관리자/maintainer가 **Settings → Pages → Build and deployment → Source: GitHub Actions**를 설정한다. 사용자가 한 번 설정해도 되고, 별도 설정 권한을 받은 에이전트가 처리할 수도 있다. HTML을 추가하는 것만으로 이 설정이 끝나지는 않는다.
2. Pages 전용 workflow가 공개 MD와 템플릿에서 HTML을 생성해 **`site/`만** artifact로 올린다. 내부 문서 폴더 전체를 업로드하지 않는다. 생성 `site/index.html`은 Git 제외 대상으로 두고 원본 MD·템플릿·스타일·선별 미디어를 관리한다.
3. 기본안은 `master`에 반영된 공개 MD·템플릿·스타일·미디어 변경 시 재생성/배포한다. 승인 전 기능 브랜치/PR에서 자동 공개하지 않는다. 병합 전에 공개가 필요하면 게시 브랜치·허용 범위를 먼저 정한다.
4. 최초 배포가 성공하고 실제 URL이 열리는지 확인한 뒤 기존 README에 **AI 에이전트 프로젝트 소개** 링크를 추가한다. 추측한 주소나 아직 없는 페이지를 링크하지 않는다.
5. Pages workflow는 사이트 artifact를 배포하며 저장소에 결과를 다시 자동 커밋하지 않는다. Unity 테스트는 우선 Editor·개발 서버가 있는 로컬 PC에서 실행한다. GitHub 호스팅 러너가 로컬 게임 서버에 접속할 수 있다고 가정하지 않는다.

사이트 링크·이미지·모바일 너비를 확인한다. 공개 대상에는 요약 txt와 선별한 작은 미디어만 포함하고 원본 영상·모든 실행 이력을 Git에 쌓지 않는다. [GitHub 공식 게시 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

## 자동 플레이 시나리오

MCP는 테스트 실행을 제어한다. 반복 가능한 입력 시나리오와 서버 결과 assertion은 클라이언트에 먼저 구현해야 한다. UI 테스트는 실제 제품의 클릭/키 입력 경로를 사용한다. 패킷 직접 송신이나 핸들러 직접 호출 테스트를 UI 조작 성공으로 보고하지 않는다. 테스트 전용 제어는 Editor/테스트 빌드에 한정한다.

| 시나리오 | 합격 근거 | 대표 자료 |
| --- | --- | --- |
| 로그인·진입 | 지정 계정의 캐릭터/Zone 상태 수신, 실패 후 재시도 | 진입 화면 PNG |
| 클릭 이동 | 지면 클릭→서버 위치 변화→다른 클라이언트 반영. UI 클릭은 이동하지 않음 | 짧은 이동 GIF |
| 키보드 스킬 | 키 입력→서버가 제공하는 시전/상태 결과→화면 표현. 채팅 입력 중 발동하지 않음 | 시전 GIF |
| 거래소 | 판매 등록→조회→다른 계정 구매→아이템 지급→판매 대금 수령. 각 단계 재조회로 수량/재화 일치 확인 | 핵심 UI PNG 또는 GIF |
| 관련 회귀 | 변경에 영향받는 재접속·중복 입력·Zone 이동·취소 처리 | 실패 시 PNG·로그 |

거래소는 `CacheLib/Handler_Bazaar.cpp`와 `MainServer/IntegrationTestBazaar.h`에 내부 처리/테스트가 있다. 조사에서 `CoreLib/PacketTypes.h`, dispatcher/NonZone 처리, `ClientCore/`에는 대응하는 거래소 클라이언트 경로를 찾지 못했다. 먼저 실제 진입점을 추적하고 없으면 서버 변경 요청 S04를 작성한다. 내부 테스트의 성공을 Unity 거래소 통과로 대신하지 않는다.

거래소 반복 검증에는 판매자/구매자 전용 계정과 준비된 아이템·재화가 필요하다. 이번 실행에서 만든 매물 ID만 사용하고 다른 플레이어 매물을 구매·취소하지 않는다. 등록 수수료·구매 재화·수령 시점은 실제 서버 계약을 따른다. 구매 성공과 비동기 아이템 지급 완료를 구분하고 제한 시간 내 재조회한다. 중복 요청으로 재화/아이템이 두 번 반영되지 않는지도 관련 변경 시 검증한다. 기존 내부 테스트의 DB 초기화·재시딩·강제 종료를 자동 실행하지 않는다.

## 캡처와 결과 보관

- PNG는 실제 Game View와 HUD가 포함되는지 확인한다. 특정 카메라만 렌더하면 Overlay UI가 빠질 수 있으므로 화면 확인용 캡처 경로를 구별한다.
- GIF/영상은 먼저 Unity Recorder의 짧은 자동 녹화를 검토한다. Recorder 5.1 문서는 Unity 6000.0 이상과 GIF/영상/이미지 시퀀스를 안내한다. 실제 설치 버전을 고정하고 작은 샘플로 확인한다. MCP 도구에 네이티브 GIF 기능이 있다고 가정하지 않는다.
- Recorder는 Editor Play mode용이다. 별도 실행 빌드는 별도 캡처 방법을 검증한다. 매 프레임 MCP 호출이나 새 녹화 시스템부터 만들지 않는다.
- 대표 기능 통과 시 GIF 하나, 실패 시 PNG와 필요한 로그를 기본으로 한다. GIF는 5~8초·낮은 프레임률·축소 해상도부터 시작하고 용량이 크면 짧은 MP4를 사용한다. 성능 측정과 녹화 실행은 분리하며 네트워크 테스트의 게임 시간을 녹화용으로 바꾸지 않는다.
- 원본 결과는 Unity 프로젝트의 `Captures/` 등 `Assets` 밖에 저장하고 Git에서 제외한다. 공개가 허용된 대표 자료만 `site/media/`로 복사한다. 원본 보관 한도는 최근 5회부터 시작한다.
- txt 요약에는 시나리오, 소스 commit/미커밋 상태, 서버 빌드·콘텐츠 기준, 기대/실제 결과, 로그·캡처 경로를 남긴다. Unity 기본 보고서는 필요한 경우 보관하되 별도 JSON 수집기는 만들지 않는다.
- 기능 테스트 결과와 캡처 생성 결과를 각각 기록한다. 녹화 실패를 기능 성공으로 숨기거나 화면 한 장만으로 기능을 통과시키지 않는다. 계정 비밀번호·토큰이 화면이나 로그에 노출되지 않게 한다.

[Unity Recorder](https://docs.unity3d.com/Packages/com.unity.recorder@5.1/manual/index.html), [설치 요구사항](https://docs.unity3d.com/Packages/com.unity.recorder@5.1/manual/installation.html)

## 시작 전에 채울 정보

1. 작업 브랜치 자동 커밋/push 허용 범위와 첫 Pages 공개 시점.
2. 테스트 서버 경로·버전·서비스 시작 권한, 계정 2개와 거래소 아이템/재화 준비 방식.
3. 스킬 키 배치·카메라 방향, 에셋 사용 범위. 미정 세부 사항은 첫 화면 샘플에서 확인한다.

역할을 추가할 필요는 없다. Coordinator가 Git/게시 진행, 구현이 변환·사이트·입력 테스트 지원, 테스트 담당이 시나리오·캡처, 문서 담당이 공개 MD를 맡는다. Slack 승인/확인과 작업 재개 구성은 [PIPELINE_GUIDE.md](PIPELINE_GUIDE.md)를 따른다.
