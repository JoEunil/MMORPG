## 성장 규칙의 저작·저장 방식

사용자 후속 결정으로 성장 규칙도 서버 C++ Data를 정본으로 둔다. 레벨별 누적 필요 EXP·승급 효과를 데이터 테이블로 관리하고 판정 코드가 조회한다. Unity가 규칙을 작성해 서버를 덮어쓰는 방식은 사용하지 않는다. 서버/클라이언트 공유는 [현재 데이터 경로](CONTENT_PIPELINE.md)의 서버 exporter→JSON→기존 Unity asset importer 방향으로 이어간다. 스킬·몬스터·성장 모두 같은 exporter/JSON formatVersion2/importer를 사용한다. GrowthData.h/Growth.inc의100행과 Unity 성장 필드는 구현했고, 실제 레벨업 로직은 후속 브랜치에서 구현·단위검증했으며 실서버 적용은 후속이다.

Lv1~100 행·단조 증가 임계값·중복 레벨·수치 범위를 exporter/importer에서 검증한다. 초기 표는 누적 EXP=50×L×(L−1)/2, Lv1 증가량0/Lv2~100 최대 HP 증가량500이다. 초기 데이터 작성용 곡선이며 밸런스 확정이나 실제 승급 적용을 의미하지 않는다. 초기 EXP50/150·HP+500과 Lv4~100 곡선은 데이터 제안이며 수치별 분기를 코드에 하드코딩하지 않는다. DB는 캐릭터의 실제 level/누적EXP/현재·최대HP를 기존 필드에 저장한다. 새 DB 규칙 테이블·런타임 .dat 로더·핫리로드는 도입하지 않는다. 기존 저장 레벨/최대HP를 로그인 때 새 표로 재계산하지 않는 정책은 유지한다.

## 선택된 첫 묶음: 초기 레벨업

**마을→일반 몬스터 사냥→EXP 축적→첫 레벨업→성장 효과 확인→마을 복귀**를 첫 구현 후보의 플레이 흐름으로 잡는다. 실제 레벨·최대 HP 변화가 끝점이다.

1. 기존 이동·Z/X/C로 사냥하고 처치 보상 EXP를 받는다. 새 임무 수락·보상 수령 버튼은 필요 없다.
2. 필요 EXP 경계를 넘으면 서버가 level과 성장 효과를 함께 갱신한다. 기존 Lv/EXP·HP/MP를 사용하고 응답 전에 수치를 올리지 않는다.
3. 같은 적과 다시 교전해 생존 여유 변화를 확인한다. 아래 검토안의 효과는 최대 HP만 증가한다. 공격력·MP·스킬·스폰·몬스터 AI는 바꾸지 않는다.

### 첫 레벨업 정책 묶음 — 수치 미승인

| 항목 | 하나의 검토안 |
| --- | --- |
| 초기 구간 | Lv1→2는 총 누적 EXP50, Lv2→3은 총 누적 EXP150. EXP를 레벨마다 차감하지 않는다. |
| 보상 리듬 | EXP0의 Lv1이 ID0(EXP10)만 처치하면 첫 변화5회, 다음 변화 추가10회다. 산술 비교이며 측정한 시간·체감 균형이 아니다. 다른 몬스터·기존 EXP에는 횟수가 달라진다. |

HP+500은 기존 최대 HP10000인 경우5%의 증가이므로 체감은 아직 약할 수 있다. 신규 캐릭터 기본값과 실제 피해·교전 관찰을 보고 묶음 전체를 조정하며 개별 수치마다 새 선택 질문을 만들지 않는다. 저장 HP/MP 초기화나 공격/스킬 하향으로 성장을 강제하지 않는다.

## 선택된 후속 방향: 회복 아이템

추천 후속은 **일반 몬스터 처치→HP포션 가방 직접 지급→I에서 선택·사용→수량 감소와 HP 회복→다음 교전**이다. 현재 후속 브랜치에 획득·사용 서버 확장과 가방 UI를 구현했고 자동 검증을 통과했다. 실제 게임 검증은 보안 창 처리·로그인 후 진행한다. 거래소 구매나 테스트 계정에 미리 넣은 물약은 신규 플레이어의 지속 공급원이 아니다.

기술 순서는 **레벨 전환→HP포션 사용 계약→처치 직접 지급 계약**이다. 사용만 구현한 단계는 완결된 아이템 경험으로 보고하지 않는다. 지급까지 연결한 뒤 MP포션을 같은 계약으로 다룰지 검토한다. 첫 레벨업과 포션 전체를 모두 첫 구현의 필수로 합치지 않는다.

희귀 확률 보상보다 짧은 사냥 안에 용도를 확인하는 확정 보상을 우선 비교한다. 이후 사용자 선택으로 일반 몬스터 ID0/1 처치마다1개·HP3000·2초·전투 중 사용을 초기값으로 확정했다. 균형 평가는 아직 하지 않았다. 첫 보상 이력·처치 횟수 기능이 있다고 가정하지 않는다. 장비·바닥 줍기·새 재료·제작·상점·골드 드롭은 이 묶음에서 미룬다.

**회복 수요도 미평가다.** 기존 관찰 maxMP10000에 X/C 비용20이면 다른 비용·회복을 빼고 단순 계산상 약500회분이다. 현재 MP포션이 필요하거나 균형이 맞는다고 주장할 수 없다. 공급량·회복량·기본 능력치는 별도 조정 제안으로 다루며 저장 HP/MP 초기화나 스킬 하향으로 수요를 강제하지 않는다.

## 영향 책임과 향후 최소 검증

- 서버 전투/캐릭터 상태: 기존 막타 EXP 지급 지점에 승급·HP 변경·dirty field 전파를 연결한다. 보상 중복을 만들지 않는다.
- 기존 저장/로드: 정상 종료 저장의 변경 필드와 재접속 보존을 대조하고 로그인 시 성장 재적용을 막는다. 캐시/DB 직접 보정은 하지 않는다.
- ClientCore/Unity: 기존 snapshot/delta와 Lv/EXP·HP 표시를 재사용한다. 필요 EXP 진행률·새 성장 창·스탯 배분은 추가하지 않는다.

향후 검증은 다음 세 묶음으로 제한한다. 현재 통과한 테스트가 아니다.

1. Lv1/EXP40에 EXP10 지급→Lv2/EXP50·최대 HP+500·생존 HP도+500. 임계값 미만·한 번에 여러 레벨·Lv99→100/100 이후 상한·필드 상한도 같은 집중 단위검증에서 확인한다.
2. 기존 고레벨·높은 EXP의 낮은 레벨·HP0 상태에서 로그인 시 무변경, 다음 정상 보상 때 필요한 승급만 적용, 이미 보유한 레벨 보너스 재적용 없음·Lv100 이후 승급 없음·EXP 정책 유지를 확인한다.
3. 정상 처치 승급→기존 HUD의 서버 확정치 반영→정상 disconnect/재접속에서 EXP/level/HP/최대 HP 유지·추가 보너스 없음 확인. 충돌 내구성·균형 성공으로 확대하지 않는다.

관찰할 완료 조건은 다음과 같다.

| 범위 | 정상 결과 | 실패·재접속 기준 |
| --- | --- | --- |
| 첫 레벨업 | 확정 임계값 미만에는 승급 없고 경계 통과 시 level과 최대 HP/생존 HP 반영. 정상 재접속 후 정합. | 중복 성장·클라이언트 선반영 금지. HP0 보존·기존 고레벨/EXP 보존·로그인 보너스 재적용 없음. |
| 회복 아이템 후보 | 처치 지급이 실제 가방에 반영되고 사용 성공 시 수량 감소·HP 회복을 함께 확정. | 가방 가득 참·수량 한도·HP가 가득 참/사망·연속 요청·끊김·저장 실패 정책 필요. 중복 지급/소비/회복과 가짜 성공 금지. 닫기는 사용이 아님. |

기존 막타 개인 보상을 유지하며 공동 분배를 확장하지 않는다. 다음 레벨 필요량은 확정 서버 기준과 연결할 때만 표시한다. 새 성장 창·포션 단축키는 기본 범위에 넣지 않는다. 구현 후 정상 경로와 가장 큰 실패 위험을 2~3개 시나리오로 확인한다. 레벨업 수치 로직은 집중2검사로 확인했다. 실제 사냥 승급·저장 재접속·드롭·회복·균형은 미실행·미평가다.

## 방향 답변과 상세 정책의 구분

의사결정 지원 담당은 위 답변을 **레벨업 우선·회복 후속** 방향에만 연결한다. EXP50/150 이후 Lv100까지의 곡선·HP+500·기존 데이터 전환·저장 정책은 이 문서에서 새로 제안한 한 묶음으로 Coordinator의 리뷰 대상이다. 이 초기 방향 답변만으로 구현 권한을 확대하지 않았다. 이후 사용자가 남은 성장·회복을 한 PR로 진행하고 추천 정책을 적용하도록 명시해 이번 서버·통신·가방 UI 연결을 진행했다. DB 직접 초기화·새 스키마·사용자 AI 변경은 포함하지 않는다.

## 성장·회복 통합 묶음 — 2026-10-29 진행 중

사용자는 PR59 병합 후 남은 작업을 한 PR로 묶어 진행하도록 요청했다. `codex/progression-loop`에 레벨업 실제 검증과 HP포션 획득·사용을 함께 모은다. 사용자가 선택한 초기 포션 정책은 일반 몬스터(ID0/1) 처치마다 HP포션(ID1)1개, 사용 시 HP3000 회복·40틱(2초) 재사용이다. 사망/HP가득 시 소비하지 않고 가방 가득/수량상한이면 미지급 안내한다. 전투 중 사용 가능, 초과 회복은 최대 HP로 제한한다. 새 바닥 드롭·우편·장비·MP포션은 이 묶음에 포함하지 않는다. 근거: request_user_input_async call_bb67cd5e5b764fccbf6c968236542a0f의 ‘추천 정책으로 진행’. 이 선택은 밸런스 평가 완료를 의미하지 않는다.

서버는 새로운 사용 요청/응답과 지급 알림을 추가하고 ClientCore·DummyClients·Unity DLL을 함께 맞춘다. 사용은 서버가 캐릭터·소유권·수량·회복 가능 상태를 확인한 후 확정한다. 클라이언트는 회복량/소비량/캐릭터 ID를 임의로 보내거나 성공을 선반영하지 않는다. 닫기·구역 전환·응답 유실 후 자동 재사용하지 않는다.

획득 대기는 CacheStorageInventory가 캐릭터·Zone 객체와 독립해 보관한다. 캐시 로드가 끝난 기존 DB 작업 안에서 지급까지 마쳐 정상 disconnect/shutdown 중 첫 보상 유실을 막는다. 새 소비/지급 경로는 WAL append 실패 시 수량을 바꾸지 않는다. 기존 HP와 인벤토리의 분리 저장·주기 fsync 때문에 비정상 종료의 원자적 복구는 보장하지 않는다. 정상 저장 완료 후 재접속을 검증하며 DB 장애는 성공으로 숨기지 않는다.

구현 전체 완료 후 정상 흐름·실패 무변경·수명 경계의 세 위험 묶음만 직접 검증한다. 이미 통과한 성장 산술2검사는 변경이 없다면 반복하지 않는다. MainServer 중간 빌드는 링크 후 기존 xcopy 후처리가 대기해 Ctrl+C로 정상 취소했다. 최종 후보는 복사 후처리를 분리해 빌드·런타임 의존성을 각각 확인한다. 현재 전체 구현·실제 게임 검증은 진행 중이다.
