# 에이전트 작업 흐름

공통 지침은 [AGENTS.template.md](AGENTS.template.md), 기능 범위는 [BRIEF.md](BRIEF.md)를 따른다. 여기서는 Coordinator와 7개 전문 역할의 진행 순서와 인계만 정의한다. 사용자는 Coordinator와만 대화하며, 지침 적용과 MCP 연결 검증 이후 기능 개발을 시작한다.

모델/추론, P01 권한 정책, 빈 프로젝트·Slack 승인/자동 재개를 포함한 구축 순서는 [PIPELINE_GUIDE.md](PIPELINE_GUIDE.md)를 따른다. P01의 서버 콘텐츠 변경은 추가 승인 없이 진행하며 보호 영역은 별도 승인을 유지한다.

## 프로젝트 준비

이 단계는 Coordinator 개발 워크플로우 시작 전에 사용자와 현재 준비 담당이 수행한다. Unity·Slack 연결과 임시 Scene 입력/캡처 시험, 테스트 서비스/계정 준비 상태를 인계한 뒤 Coordinator를 시작한다. 실제 게임 기능은 이 단계에서 만들지 않는다.

1. 같은 Game 저장소의 `master` 기준 commit을 확인하고 전용 브랜치/별도 worktree를 준비한다. 기존 미완료 변경은 보존한다. 제안 브랜치는 `codex/unity-ai-client`다. [DELIVERY.md](DELIVERY.md)의 Git·게시 경계를 따른다.
2. `UnityClient/`에 새 Unity 프로젝트를 두고 Editor `6000.0.47f1` 기준으로 패키지 호환성을 확인한다. Unity 7을 선행 조건으로 두지 않는다. `Assets`, `Packages`, `ProjectSettings`와 `.meta`는 관리하고 `Library`, `Temp`, `Logs`, 원본 녹화·로컬 자격 증명은 제외한다.
3. 공통 템플릿을 작업 체크아웃 루트 `AGENTS.md`로 적용한다. 승인 범위 밖의 기존 서버/ClientCore 파일은 읽기만 한다. ClientCore 원본과 Unity에서 사용할 DLL의 기준을 기록하고 수정 소스 사본·옛 DLL을 중복 포함하지 않는다.
4. [MCP_SETUP.md](MCP_SETUP.md)에 따라 대상 프로젝트·Console·컴파일·임시 입력 테스트·PNG/GIF와 Slack 왕복/재개를 확인한다. 서버 소스와 실행 빌드 기준도 기록한다. 준비 완료 후 사용자의 시작 지시로 Coordinator를 실행하고 작은 게임 기능부터 전체 개발 흐름을 검증한다.

## 역할 활성화

Coordinator는 주 채팅을 맡고 `roles/coordinator.md`를 따른다. 나머지 7개 역할은 필요할 때 하위 에이전트로 배정한다. 역할 문서가 있다는 이유만으로 에이전트가 자동 생성되거나 모델이 바뀌지는 않는다. 2026-10-18 사용자 지시로 프로젝트 차원 고정 동시 인원 제한은 해제했다. 도구가 제공하는 슬롯 안에서 파일 소유권과 의존성이 분리된 작업을 병렬화한다. Editor 조작권은 한 번에 한 명이며 같은 파일의 동시 편집은 금지한다.

| 역할 | 지침 | 주로 호출하는 시점 |
| --- | --- | --- |
| Coordinator | [coordinator.md](roles/coordinator.md) | 주 채팅에서 진행 전체 관리 |
| 구현 | [implementer.md](roles/implementer.md) | 명세 확정 후 구현·수정 |
| 리뷰 | [reviewer.md](roles/reviewer.md) | 변경 고정 후 독립 검토 |
| 테스트 | [unity-tester.md](roles/unity-tester.md) | 준비 검증·기능/통합/빌드 검증 |
| 기획 | [planner.md](roles/planner.md) | 기능 착수·요구 변경 |
| 아트 | [asset-artist.md](roles/asset-artist.md) | 미술 샘플·리소스 제작·배치 |
| 진행 문서 | [documenter.md](roles/documenter.md) | 작업 묶음 완료·중요 결정 |
| 서버 변경 요청 | [server-analyst.md](roles/server-analyst.md) | 계약 조사·불일치·데이터화 검토 |

첫 실행에는 공통 지침 + 해당 역할 문서 + 아래 작업 카드면 충분하다. Codex 커스텀 에이전트를 사용하는 환경에서는 새 프로젝트의 `.codex/agents/`에 역할별 TOML을 둘 수 있다. 예를 들어 구현 역할의 최소 예시는 다음과 같다.

```toml
name = "client_implementer"
description = "확정된 명세에 따라 Unity 클라이언트를 최소 변경으로 구현한다."
model = "gpt-6-luna"
model_reasoning_effort = "medium"
developer_instructions = """
먼저 루트 AGENTS.md와 docs/unity-client/roles/implementer.md를 읽고 따르라.
총괄이 지정한 변경 범위만 구현한다. 기존 서버와 원본 ClientCore는 승인된 범위만 수정한다.
P01에 따라 서버 콘텐츠는 자율 변경하고 보호 영역은 별도 승인 범위를 따른다.
"""
```

나머지 전문 역할도 같은 형식으로 고유 이름·해당 역할 파일·모델을 지정하면 된다. Coordinator는 주 채팅의 지침/모델로 설정하므로 Coordinator 하위 에이전트를 하나 더 만들지 않는다. 선택한 환경이 커스텀 역할 설정을 지원하는지, 모델 설정이 실제 적용됐는지 실행 시 확인한다.

하위 에이전트는 부모 세션 권한과 MCP를 상속한다. 역할 TOML의 “읽기 전용” 문장이나 `sandbox_mode` 항목으로 별도 보안 경계가 만들어진다고 가정하지 않는다. MCP 연결과 파일 권한은 부모 세션에서 설정한다. [공식 커스텀 에이전트·권한 안내](https://learn.chatgpt.com/docs/agent-configuration/subagents)

역할 배정·검토·재시도는 Codex Coordinator가 수행하고, MCP는 Unity 조작 도구를 제공한다. 에이전트 간 Slack 봇은 만들지 않는다. Slack에서 사용자 회신을 받아 자동 재개하려면 수신·작업 재개 연결을 별도로 검증한다. 기존 연결이 제공하지 않을 때만 작은 로컬 수신기를 검토한다. 중단 시 마지막 검증 상태에서 재개하며 진행 중 테스트를 성공으로 간주하지 않는다.

Slack 요청·승인·진행·결과는 사용자 지시에 따라 변경 단위마다 새 스레드로 묶고, 작업 카드에 thread ts를 기록한다. 기존 스레드에서 받은 유효 승인은 원문 링크로 이어받는다. Coordinator 수신 대상은 임의 변경하지 않으며, 자동 전달이 검증되지 않은 변경 스레드는 커넥터로 직접 읽는다.

| 단계 | 작업 | 완료 근거 |
| --- | --- | --- |
| 0 | 기획·조작·에셋 방향, 프로젝트와 MCP 준비 | 올바른 프로젝트, 컴파일/작은 테스트, Coordinator 배정부터 리뷰·실행·캡처까지 한 차례 검증 |
| 1 | 서버 계약 조사, 허용된 ClientCore 호환 수정·Unity 연결 | opcode/필드 폭/순서/엔디언/프레임 길이/Full·Delta 의미, profile·chat 형식과 연결 종료 경로 검증 |
| 2 | 로그인→캐릭터 선택→한 Zone 진입, 기본 도형과 카메라 | 실제 테스트 계정으로 진입, 서버 ID/좌표 확인, 로그인 실패와 재시도 처리 |
| 3 | 이동·다른 플레이어·몬스터·기존 스킬·HUD·조회 UI | 두 계정/두 클라이언트에서 같은 서버 결과 확인. UI만 성공 처리하지 않음 |
| 4 | 첫 구역의 지형 장식·모델·애니메이션·VFX·UI 통합 | 실제 플레이 화면의 시인성·일관성·목표 성능 검증, 사용자 미술 확인 |
| 5 | 기존 스킬/몬스터/맵 데이터 export 후보 | ID/범위/참조 검증, 기존 값과 비교, 동일 입력의 재출력 일치. P01 콘텐츠 범위는 자율 적용하며 보호 영역 변경만 별도 승인 |

단계 1과 화면 샘플 준비는 병행할 수 있다. 데이터 계약 초안도 일찍 작성하되 현재 동작을 확인하기 전에 전체 데이터 도구를 만들지 않는다.

## 기능 하나의 반복 흐름

1. **Coordinator → 기획:** 이번 사용자 목표와 기존 결정을 전달한다. 기획은 필요한 경우에만 짧은 기능/UI 명세와 수용 조건을 갱신한다. 이미 명세가 있는 작은 수정은 이 단계를 반복하지 않는다.
2. **Coordinator → 서버 분석(필요 시):** 구현에 필요한 서버 계약이나 불일치를 확인한다. P01 콘텐츠 범위는 추가 승인 없이 배정하고, 보호 영역 변경만 요청안과 영향을 정리해 Coordinator가 사용자 승인을 받는다.
3. **Coordinator → 구현/아트:** 확정 명세, 변경 파일, 완료 조건, 검증, 승인 범위를 작업 카드로 전달한다. 코드와 외부 에셋 준비는 병행하되 Scene/Prefab 통합은 조작권을 인계해 순서대로 한다.
4. **리뷰 → Coordinator → 구현:** 완성된 diff와 계약을 독립 검토하고 Coordinator가 필요한 수정 범위를 전달한다. 리뷰는 코드를 대신 고치지 않는다. 수정 후 변경을 고정하고 커밋 또는 파일 목록/해시로 검토·테스트 대상을 식별한다.
5. **테스트 → Coordinator:** Editor 조작권을 받고 컴파일, 관련 자동 테스트, 실제 서버 시나리오, 화면/빌드를 검증한다. 실패하면 근거를 Coordinator에게 보내 구현 또는 기획으로 돌린다.
6. **Coordinator → 진행 문서:** 완료 조건의 근거를 확인하고 상태를 결정한다. 확인된 결과·결정·남은 일과 필요한 공개 설명을 기록하게 한다. 대표 자료의 생성 결과는 기능 테스트 결과와 구별한다. Coordinator만 허용된 범위에서 커밋/게시하고 사용자에게 보고한다.

모든 작업에 8개 역할을 의무적으로 통과시키지 않는다. 단순 텍스처 교체에 전체 코드 리뷰나 서버 분석을 호출하지 않으며, 문서 갱신만 필요한 경우 개발 역할을 호출하지 않는다. Coordinator는 사용자의 새 요구/답변을 필요한 역할에만 전달한다. 전문 역할의 질문은 Coordinator가 기존 결정으로 먼저 해소하고, 사용자 결정이 필요한 것만 묶어서 올린다.

Editor 조작권은 총괄이 작업 카드에 담당자와 현재 상태(편집/검증)를 적어 관리한다. 처음부터 잠금 서비스나 워크플로우 엔진을 만들지 않는다. 테스트 중 `Assets/Packages/ProjectSettings` 쓰기는 모두 멈춘다. 리뷰는 고정된 diff를 읽으므로 Unity 테스트와 병행 가능하다.

## 작업 카드

```text
작업 ID / 역할:
목표: 사용자가 볼 수 있는 결과 한 가지
기준: BRIEF의 해당 항목 + 실제 코드/API/프로토콜 근거
수정 허용: 정확한 파일/폴더
고정 계약: 입력·출력·좌표·ID·이벤트 수명 등 이번 작업에 필요한 것만
완료 조건: 관찰 가능한 2~5개 항목
검증: 실행할 테스트/서버 시나리오와 필요한 계정
모델/추론: 작업 성격에 맞춘 모델 ID와 수준
Editor 조작권: 담당자 또는 없음
변경 허용: ClientCore/서버 각각 불허 또는 사용자 승인 ID·개정·정확한 범위
인계: 변경 파일·검증 근거·미해결 문제
```

매 역할에 독립적인 대형 명세를 만들지 않는다. 기획 명세는 기획 담당, 서버 계약은 서버 분석 담당, 현재 진행은 문서 담당이 소유한다. Coordinator는 변경을 수용하고 영향받는 역할에 전달한다. Coordinator와 전문 역할이 같은 문서를 동시에 편집하지 않는다.

## 서버 변경 요청 양식

아래 양식은 콘텐츠 자율 변경 범위 밖의 보호 영역에만 사용한다. 서버 콘텐츠는 작업 카드에 허용 근거 `P01 콘텐츠 자율 변경`을 적고 진행한다.

```text
요청 ID / 상태: 제안 중, 승인 대기 (기본)
필요한 이유: 현재 동작과 원하는 동작, 클라이언트만으로 해결할 수 없는 근거
정확한 범위: 서버 파일·데이터·프로토콜·DB·설정별 변경 유무
후보: docs/unity-client/의 설명/patch 또는 UnityClient/의 export 후보
호환성: 기존 클라이언트/서버와 데이터의 영향, 재빌드·재시작 필요 여부
검증/복구: 확인 방법과 기존 버전으로 되돌리는 방법
승인 질문: 이 범위의 변경을 적용해도 되는지
사용자 답변: Slack 승인자 ID·스레드/메시지 링크·요청 개정·원문. 없으면 미승인
```

요청안 작성과 실제 서버 계약 확인은 서버 변경 요청 담당이, 사용자에게 설명하고 승인받는 일은 Coordinator가 맡는다. 공통 지침의 사전 승인 규칙은 사용자가 직접 요청한 제한이다. 승인 질문에는 그 이유를 짧게 밝힌다. Coordinator가나 리뷰 담당이 대신 승인할 수 없다.

승인 후 같은 코드 구현 역할에 해당 변경을 배정한다. 승인된 범위의 작은 서버 변경은 같은 기능 브랜치에서 클라이언트와 통합할 수 있다. 원본 Game의 미완료 변경을 덮어쓰지 않는다. 검증·재빌드·로컬 테스트 재시작을 요청 범위에 명시하면 반복 승인 없이 이어간다. 병합·배포·운영 DB 변경까지 포함된 것으로 간주하지 않는다.

콘텐츠 변경은 사용자가 자율 진행을 허용했다. 보호 영역의 추가 자유화는 Coordinator가 임의로 적용하지 않는다.

## 결과와 중단 기준

작업 결과는 `통과 / 실패 / 환경 차단 / 승인 대기 / 미실행`으로 구분한다. txt에 테스트 대상 버전, 서비스/콘텐츠 버전, 완료 조건별 결과, 실패 로그·스크린샷 경로만 남긴다. Unity가 생성하는 원본 테스트 보고서는 필요할 때 함께 보관한다.

동일 실패 2회, API/기획 불명확, 다른 역할의 파일 수정 필요, 서버 승인 필요 시 총괄에게 인계한다. 역할은 남겨 두되 호출하지 않을 수 있다. 자동화는 승인된 작업 묶음을 완료할 때 종료하며 무기한 재시도하지 않는다.

## 새 프로젝트의 Coordinator에게 줄 시작 지시

```text
너는 이 프로젝트의 Coordinator가다. 나는 너와만 소통한다.
AGENTS.md와 docs/unity-client/WORKFLOW.md, BRIEF.md,
roles/coordinator.md를 읽고 7개 전문 역할을 필요한 때만 배정하라.
master 기준 전용 브랜치와 같은 저장소의 작업 경계를 확인하라.
DELIVERY.md도 읽고 커밋·push·병합·공개 허용 범위를 구분하라.
먼저 올바른 Unity MCP 연결, 컴파일과 작은 테스트를 확인하라.
작은 기능 하나의 배정→구현→리뷰→실행·캡처가 통과하면 첫 플레이 구역을 시작하라.
확정된 범위 안의 구현과 P01 서버 콘텐츠 변경은 자율 진행하되 보호 영역 변경만 요청안을 준비해 내 승인을 받아라.
전문 역할의 질문과 결과는 네가 취합하고 필요한 결정만 나에게 전달하라.
```

Unity 입력 검증은 INPUT_TEST_BATCH.md에 변경별로 모아 배치 실행한다. 현재는 사용자 입력 테스트 보류 지시를 유지하며, 컴파일·정적 리뷰는 계속한다. 재개 지시 후 최종 버전 동결/중복 공통 flow 병합/단일 Editor 조작으로 실행한다.
