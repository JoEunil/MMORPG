# 공통 개발 기준

2026-10-22 사용자 작성안을 현재 Unity·ClientCore 구조와 운영 정책에 맞춰 반영했다. 모든 구현·코드 개선·리뷰에 적용한다. 목표는 코드 생성량이 아니라 **요구사항을 만족하는 가장 작고 일관된 구현**이다.

## 먼저 구조를 확인한다

- 수정할 코드와 호출부, 의존성, 기존 관례를 읽고 현재 책임 안에서 해결한다. 기존 시스템과 나란히 동작하는 별도 구현을 만들지 않는다.
- 새 클래스·인터페이스·Manager·계층은 현재 필요한 책임과 이유가 있어야 한다. 미래 확장·테스트 편의만을 위한 범용 프레임워크, 임시 구조를 만들지 않는다.
- 간단한 직접 구현을 우선한다. 함수나 파일의 줄 수만으로 분할하지 않으며 긴 클래스도 실제 책임·수명 경계가 확인될 때만 나눈다.

## 책임에 맞게 파일을 둔다

- 기능·하위 시스템·런타임 책임을 기준으로 기존 모듈에 통합한다. 새 제품 파일·타입·폴더를 작업 번호·단계·스프린트·에이전트 이름으로 명명하지 않는다.
- 기존 C02/C04 같은 이름은 정리 후보이지 즉시 일괄 변경할 근거가 아니다. 관련 호출과 직렬화 참조를 확인해 안전한 묶음에서 바꾼다. 내부 작업 기록의 번호는 유지할 수 있다.
- 한 클래스를 위해 폴더를 늘리거나 중복 Manager/Utility를 만들지 않는다. 예시 디렉터리 구조를 그대로 복제하지 않는다.
- Unity 이동·이름 변경 시 .meta와 GUID, Scene·Prefab·ScriptableObject·직렬화 필드, Resources/Addressables 경로, asmdef/Editor 경계, 문자열·리플렉션 참조를 확인한다. 타입·필드 호환 처리가 실제 필요할 때만 적용한다.

## 단순하게 만들되 경계는 지킨다

- 실제 요구에 필요한 코드만 쓴다. 의미 없는 래퍼·전달 전용 함수·별칭·단일 사용 추상화·중복 상태를 제거한다. 수명·외부 경계나 의미를 드러내는 함수와 변수까지 줄이지 않는다.
- 내부에서 보장된 조건을 계층마다 반복 검사하지 않는다. 패킷·외부 입력·파일 작업·파괴된 Unity 객체처럼 실제로 실패할 수 있는 경계는 검증한다.
- 삭제 전 코드 호출뿐 아니라 Unity 직렬화·빌드 심볼·리플렉션·에디터 도구 참조까지 조사한다. 사용하지 않는다는 근거가 없으면 보존하고 불확실성을 남긴다.
- 주석은 비자명한 결정·불변식을 설명한다. 과도한 로그·디버그 구조·근거 없는 호환 코드·실패를 숨기는 기본값/예외 무시는 추가하지 않는다.

## 상태와 통합을 확인한다

- 서버 확정 상태·ClientCore 상태 적용·Unity 화면 표현의 소유권을 구분한다. 같은 런타임 상태를 여러 곳에 복제해 독립적으로 갱신하지 않는다.
- 프로토콜·패킷 순서·좌표·구역 소유권·Full/Delta 초기화·객체 수명과 정리를 보존한다. 컴파일만으로 통합 완료를 선언하지 않는다.
- Unity 객체는 올바른 메인 스레드와 수명 안에서 다룬다. Unity 기능이 필요 없는 로직에 MonoBehaviour나 GameObject·전역 Manager를 붙이지 않는다.
- Update·패킷 루프·엔티티 갱신의 LINQ·할당·반복 검색은 실제 실행 경로와 비용 근거가 있을 때 정리한다. 성능 근거 없이 풀·캐시·동시화 계층을 추가하지 않는다.
- 계약이나 서버 동작 변경은 영향과 호환성을 명시하고 기존 권한 정책을 따른다. 동작 보존 정리로 위장하지 않는다.

## 최소 검증과 협업

- 시작 전에 작업 트리와 담당 파일을 확인하고 사용자·다른 에이전트 변경을 보존한다. 같은 파일을 동시에 수정하지 않는다.
- 기존 통과 기록은 후보·동작이 같은지 확인해 재사용한다. 문서만 수정했으면 링크/일관성 검사로 끝내며 컴파일·게임 테스트를 새로 요구하지 않는다.
- 코드 변경은 직접 영향이 있는 통합 흐름과 중요한 경계만 묶음 끝에 확인한다. 모든 정리마다 로그인·구역 왕복·재접속·프로파일링 전체를 반복하지 않는다.
- 제출 전 변경 diff의 중복·불필요한 계층·잘못된 위치·참조 파손을 확인한다. 실패·차단·미실행을 숨기지 않으며 정리의 실제 효과와 남은 위험을 짧게 보고한다.
- 코드 개선은 기능 구현에 관련된 범위 또는 별도 배정한 정리 묶음 안에서 진행한다. 다른 기능을 만들거나 무관한 대규모 리팩터링을 끼워 넣지 않는다.
