Coordinator 역할은 docs/unity-client/roles/coordinator.md를 따른다. 전문 역할은 공통 지침과 배정된 역할 문서를 함께 읽는다. 모델·추론은 PIPELINE_GUIDE.md의 권장안이며 문서 설치만으로 실행 설정이 바뀐 것으로 보고하지 않는다.

Slack 수신기는 현재 Unity Client Coordinator `01a14d46-8b23-7590-8ad5-7efc20f8ecd9`와 등록된 변경 스레드만 대상으로 한다. 이전 준비 수신기 설정/상태는 보존하고 대상 채팅을 임의 변경하지 않는다. 로컬 테스트 서버의 시작·정상 종료·정상 재시작과 전용 계정 2개 사용은 승인된 일상 테스트 작업이다. 원본 ClientCore의 Unity 최소 호환 수정과 관련 검증을 통과한 작업 브랜치 커밋도 허용됐다. push·PR 생성·병합·공개는 아래 최종 승인 규칙을 따른다. 실제 준비 상태는 `LOCAL_PREPARATION.md`를 확인한다.

Slack은 변경 묶음별 스레드에 핵심 결과만 남긴다. 작은 단계 완료마다 재개 명령을 요구하지 않으며, 실행 플랫폼이 직접 승인을 요구한 경우에만 해당 차단과 사유를 별도로 알린다.
Slack 발신자는 사용자 계정이 아니라 설치된 Unity Coordinator 앱이어야 한다. 사용자 명의 커넥터 발신을 사용하지 않는다. 기존 DPAPI BotToken과 auth.test로 workspace·bot user를 확인한 경로를 사용하고 비밀 값은 인자/로그/저장소에 남기지 않는다. 현재 전용 발신 도구는 UnityClient/Tools/Send-CoordinatorSlack.ps1이며 읽기는 커넥터를 사용할 수 있다. 승인 요청에는 필요한 최소 정보만 담는다.
사용자 추가 지시: 프로젝트 보호 영역의 사람 승인은 지정 Slack 앱 스레드에서 처리하며 Coordinator가 자체 절차로 같은 범위의 채팅 중복 승인 질문을 만들지 않는다. 다만 실행 플랫폼의 managed sandbox/auto-review는 별도 통제다. 플랫폼 거절을 설정 약화·다른 실행 경로·메시지 출처 재분류로 우회하지 않고 해당 변경 Slack 스레드에 실제 차단 사유를 기록한다. 프로젝트 문서만 바꿔 플랫폼 권한까지 조정됐다고 보고하지 않는다.
Unity 입력 테스트는 구현 계획의 한 단계 또는 작업 묶음 전체가 끝나고 리뷰 가능한 상태로 동결된 뒤 한 번의 배치로 수행한다. 저작 중에는 반복 실행하지 않고 테스트 중 에셋 쓰기를 멈춘다. 디자인 방향은 밝은 판타지 MMORPG 느낌이며, 이 선호로 서버에 없는 기능·가짜 수치·더미 UI를 추가하지 않는다.

## Coordinator 중심 운영과 착수 조건

- Coordinator(총괄)이 사용자의 유일한 일반 대화 창구다. 사용자는 각 전문 역할을 직접 지휘할 필요가 없다.
- 역할은 Coordinator·코드 구현·코드 리뷰·테스트·기획·아트·진행 문서·서버 변경 요청의 8개다. 전문 역할은 질문/제안/실패를 Coordinator에게 보고하고, 사용자에게 직접 질문하거나 다른 채팅에 메시지를 보내지 않는다. 필수 도구 권한 승인은 플랫폼 규칙을 따른다.
- 지침을 적용하고, 서버 읽기/클라이언트·문서 쓰기 경계와 Unity MCP 대상·컴파일·작은 테스트를 확인한다. 작은 기능 하나로 Coordinator 배정→구현→리뷰→실행·캡처까지 검증한 뒤 본 개발을 시작한다. 준비 문서 작성은 개발 시작이나 에이전트 실제 실행을 의미하지 않는다.
- Coordinator는 승인된 목표 안의 일상적인 구현 결정을 처리한다. 사용자는 목표/범위 변경, 미술 방향 확인, 서버 변경 승인 등 필요한 결정만 한다.
- 작업 단위 완료는 정지 지점이 아니다. Coordinator는 결과를 기록한 뒤 기존 목표·허용 범위 안의 다음 작업을 자동으로 선택하고 진행한다. 단순 완료 보고 뒤 사용자에게 `계속`, `재개`, 다음 단계 승인을 요구하지 않는다.
- 기본 소유권: 기획은 `BRIEF.md`, 서버 분석은 서버 계약/변경 요청 문서, 문서 담당은 `PROGRESS.md`의 기록을 맡는다. Coordinator는 작업 카드와 판단을 맡고 각 문서를 동시에 편집하지 않는다. 실제 파일은 필요할 때만 만든다.

## 서버 승인 경계 — 모든 역할에 적용

**승인 원칙:** 작업 브랜치 안의 구현·수정·빌드·리뷰·로컬 테스트는 승인된 프로젝트 목표 안에서 진행한다. 중요한 코드베이스 변경은 후보 diff와 검증 결과를 모두 준비한 뒤 **PR 생성 직전** 한 번만 승인 요청한다. 작은 구현 선택, 일반 콘텐츠 변경, 테스트 서버 시작·정상 재시작, 같은 후보의 재빌드·재시험에는 승인 요청을 만들지 않는다. 강제 종료, 데이터 삭제/초기화, 비밀·권한 변경, 비용 발생, 외부 공개처럼 실행 전에 되돌리기 어렵거나 범위를 벗어나는 작업만 사전 승인을 유지한다.

1. 일반 작업 범위는 `UnityClient/`, `site/`, `docs/unity-client/`, 기존 게임 기능을 위한 ClientCore·서버·콘텐츠의 최소 변경과 README·지침·ignore·Pages 설정이다. 관계없는 리팩터링과 기능 확대는 하지 않는다.
2. 중요한 ClientCore·서버·DB 계약·프로토콜·Zone/큐/락/풀 변경은 서버 분석 담당이 원인, 최소 diff, 호환성, 검증·복구 방법을 정리한다. 구현과 로컬 검증까지 마친 후보를 Coordinator가 독립 리뷰한 뒤 PR 직전 사용자에게 한 번만 승인 요청한다.
3. 승인 요청 전에는 커밋 가능한 후보, 리뷰 결과, 테스트 결과, 남은 위험과 복구 방법을 준비한다. 아직 구현·테스트하지 않은 계획만으로 승인을 요구하지 않는다.
4. 승인 대기 단계에서는 PR 생성·push·병합·공개를 멈춘다. 승인된 범위 안의 수정과 재검증마다 재승인받지 않는다. 범위가 실질적으로 커지면 최종 요청에 추가분을 포함한다.
5. 로컬 테스트 서비스의 시작·정상 종료·정상 재시작, 같은 후보의 빌드 교체, 지정 테스트 계정의 정상 게임 상태 변경은 일상 테스트 권한에 포함된다. 강제 종료, DB 초기화·파괴적 마이그레이션·재시딩, 운영 환경 조작은 사전 승인 없이는 수행하지 않는다.

## 구현 범위와 단순성

- 게임은 기존 서버 기능을 보여주는 3D 쿼터뷰 클라이언트다. 길드·공성전·펫 등 서버에 없는 시스템과 이를 위한 UI·더미·예비 구조를 추가하지 않는다. 콘텐츠 자율 변경도 기존 기능 범위 안에 한정한다.

- 현재 작업의 관찰 가능한 완료 조건만 구현한다. 서버에 없는 기능을 일반 MMO 관례라는 이유로 추가하지 않는다.
- ClientCore의 네트워크/ViewModel/ViewData/dispatcher 경계를 재사용한다. 원본 한 곳에서 유지하고 DLL 등 확인된 한 방식으로 Unity에 연결한다. 원본 수정은 사용자 허용 범위에서만 수행하며 별도 수정 사본을 장기 유지하지 않는다.
- 구현이 하나인 기능에 새 인터페이스·팩토리·범용 Manager·DI/EventBus/ECS 프레임워크를 추가하지 않는다. 기존 경계와 필요한 테스트 지점은 유지한다.
- 성능 근거 없는 풀링·캐싱·동시화, 예비 확장 구조, 관계없는 리팩터링을 하지 않는다. 데이터 export는 필요한 타입만 다루며 범용 코드 생성기를 만들지 않는다.
- 짧게 만들기 위해 패킷 길이 검증·오류 처리·연결 해제·이벤트 정리·메인 스레드 반영을 제거하지 않는다.
- 서버 wire format은 실제 실행 경로와 대조한다. enum 이름이나 이전 클라이언트 코드만으로 기능 지원을 단정하지 않는다.
- 서버의 수치·판정·결과를 기준으로 표시한다. 클라이언트 보간/예고와 서버 확정 상태를 구분한다.
- 새 유료 서비스·유료 에셋 구매는 사용자 허용 예산 안에서만 한다. 미확정이면 후보를 제시한다.

## 협업과 검증

- 구현자는 새 추상화·전달 전용 함수·별칭 변수·중복 저장 상태에 현재 필요성이 있는지 확인하고 근거 없는 부분을 제거한다. 의미 있는 지역 변수·스냅샷·외부 경계 검증은 유지한다. 상세 기준은 `roles/implementer.md`를 따른다.
- 구현 계획을 시작할 때 테스트 목표·포함/제외 범위·기대 결과·실행 비용·종료 조건을 정하되, 실행은 한 단계 또는 계획한 작업 묶음의 구현·리뷰가 모두 끝난 뒤 한 번의 배치로 수행한다. 중간 컴파일 확인과 정적 검토를 전체 기능 테스트로 확대하지 않는다. 필요한 검증 통과 후 새 변경·실패·미해결 위험이 없으면 종료한다.

- Coordinator가 승인된 실행 범위 안에서 7개 전문 역할을 필요할 때 배정한다. 모두 상시 실행하지 않으며 하위 에이전트는 임의로 인원을 늘리지 않는다. 2026-10-18 사용자 지시로 전문 역할의 프로젝트 차원 고정 동시 인원 제한을 해제했다. 실행 도구가 제공하는 슬롯 안에서 독립적인 파일·환경·의존성을 가진 작업을 적극 병렬화한다. 플랫폼 슬롯 수가 변경된 것으로 표현하지 않는다. 구현/테스트 파일은 한 명에게만 소유권을 준다.
- 동시에 같은 파일을 편집하지 않는다. Scene·Prefab·Material·`.meta`·패키지/프로젝트 설정은 총괄이 지정한 한 명만 수정한다. 필요한 파일만 소유하고 광범위한 재저장을 피한다.
- Unity Editor/MCP 조작 담당은 한 번에 한 명이다. 조작권은 기본 Unity 테스트 담당, 에셋 임포트/배치 때는 명시적으로 인계한다.
- 테스트가 진행 중이면 누구도 `Assets`, `Packages`, `ProjectSettings`를 수정하거나 재임포트하지 않는다. 외부 파일 수정도 자동 컴파일을 유발할 수 있다.
- 검토한 변경과 테스트한 변경이 같아야 한다. 이후 수정되면 영향을 받는 검증만 다시 수행한다.
- 테스트는 실제 관찰 결과를 확인한다. 테스트 삭제·assertion 완화·실패 은폐로 통과시키지 않는다. 미실행·차단·실패·통과를 구분한다.
- 보고는 변경 파일, 완료 조건별 근거, 실행한 검증, 남은 문제로 짧게 작성한다. 측정/실행 요약은 txt로 남기며 불필요한 JSON 결과 수집 체계를 만들지 않는다.
- 같은 원인으로 두 번 수정해도 해결되지 않으면 총괄에게 재현·시도·로그를 넘긴다. 작업 크기나 모델을 재검토하고 무한 재시도하지 않는다.
- 사용자 변경과 기존 산출물을 보존한다. 비밀번호·세션 토큰·비밀 설정은 문서/스크린샷/로그에 남기지 않는다.
- 문서 담당은 Coordinator의 확인과 실행 근거를 기록하며 승인·성공을 만들어내지 않는다. 문서 갱신 지연만으로 독립적인 개발 작업을 멈추지 않는다.
- Coordinator만 허용된 범위의 Git 통합/게시를 수행한다. 커밋·push·병합·공개 권한을 구분하고, 다른 역할은 임의로 실행하지 않는다. 기존 미완료 변경을 일괄 커밋하지 않는다.
- 공개 HTML은 검증된 내용과 선별한 미디어만 담는다. 자동 UI 테스트는 실제 입력 경로와 서버 결과를 확인하며 내부 핸들러 호출을 UI 통과로 대신하지 않는다.
- 공개 결과의 원본은 `SHOWCASE.md`이며 HTML은 생성 산출물이다. 생성 HTML의 본문을 별도로 편집하지 않는다.
- 에이전트 간 작업 지시는 Codex 내부에서 처리한다. Slack에는 사용자가 이해할 수 있는 핵심 요약만 올린다: `한 일`, `막힌 점과 해결`(있을 때만), `최종 테스트 결과`, `다음 작업`을 각각 한 문장 이내로 적는다. 경로·PID·hash·세부 로그는 문서에 둔다. 승인 요청은 PR 직전 `승인 <짧은 ID>`처럼 모바일에서 전체 복사하기 쉬운 짧은 명령 하나와 변경 효과·주요 위험만 적는다.

## 권한 적용 시 주의

이 문서는 행동 지침이며 파일 접근을 기술적으로 차단하는 장치는 아니다. 같은 저장소에서도 쓰기 허용 폴더와 보호할 서버 경로를 명시하고 가능한 권한 제한을 적용한다. 저장소 루트 전체가 쓰기 허용된 환경을 서버 읽기 전용으로 강제한 상태라고 표현하지 않는다. 부모 세션 권한과 MCP 서버 프로세스 권한도 확인한다.


## AI-AGENT 소개 사이트 — 2026-10-19 사용자 갱신

공개 웹의 목적·콘텐츠·경험 평가·버전별 캡처·시각 확인·완료 기준은 사용자 작성안을 반영한 `docs/unity-client/PORTFOLIO_GUIDE.md`가 현재 기준이다. 공개 작업을 배정받은 역할은 이 파일을 함께 읽는다. 목적은 결과와 AI 활용 경험을 보여주는 제출용 포트폴리오이며, 확인되지 않은 경험이나 감상을 만들어내지 않는다. 이전 단일 소개 페이지/내부 진행 보고 방식보다 이 기준이 우선한다.

최신 목적 보정: 사이트는 **포트폴리오 제출 시 AI를 활용해 개발한 과정과 결과물을 별도로 보여주는 웹 포트폴리오**다. AI 에이전트 소개 한 페이지나 내부 진행 보고서가 아니다. 홈에서 결과물을 먼저 보여주고 작업 목록/상세/화면 이력으로 링크 탐색하게 한다. 각 작업은 자연어 제목과 '무엇을 만들었는지·어떤 문제를 어떻게 풀었는지·결과가 어떤지'를 짧게 설명한다. C08/C09 같은 내부 번호, PR/병합/승인 상태, 테스트 개수·커밋 해시를 공개 본문에 나열하지 않는다. 상세 기술 근거는 저장소 링크로 분리한다. 실제 캡처를 중심으로 버전별 변화와 이전 화면을 보존하며, 현재의 숫자 텍스트 거래소 UI 등은 개선 중인 중간 결과물로 구분한다. 긴 PPT식 슬라이드/과한 장식 문구/문서 전체 복제를 피한다. 초안은 첫 배포 테스트용으로 게시하고 이후 이 목적에 맞게 전면 개편한다. 개발 묶음마다 작업 상세·현재 결과·버전별 대표 캡처를 함께 갱신한다. 이 갱신이 아래의 단일 소개 페이지 방식보다 우선한다.

기본 github.io 주소로 소개 사이트·GitHub Actions Pages 환경을 제작한다. Source 설정은 사용자가 완료했다. PR 전에 로컬 웹 미리보기와 실제 브라우저 캡처를 제공한다. 첫 확인 이후 개발 작업 묶음의 검증된 결과를 문서 담당의 SHOWCASE/캡션 → 기존 구현 담당의 HTML/선별 미디어 → 공개 내용·링크·필요 화면 확인 → 승인된 Git 통합 → master Pages 배포와 URL 확인까지 이어간다. 공개 내용 변화가 없으면 이유만 기록한다. PR은 build/artifact만 수행하며 정식 배포는 master 기준이다. PR 직전 Slack 최종 승인 절차를 유지하고 게임 검증을 사이트 갱신 때문에 반복하지 않는다.

## Unity 입력 검증 배치

Unity 마우스·키보드 입력 테스트는 최신 C04 사용자 지시로 재개됐다. 동결/독립 리뷰 후 묶인 배치를 실행한다. 기능마다 즉시 Play/UI 입력을 반복하지 않고 docs/unity-client/INPUT_TEST_BATCH.md에 변경별 검증을 모은다. 재개 승인은 실제 사람 사용자의 명시 지시로 확인됐으며 이후 다시 보류 지시가 오면 자동 재개하지 않는다. 입력이 없는 코드·에셋 저작, 컴파일, 정적 리뷰는 계속한다. 재개 시 최종 검토 버전을 동결하고 하나의 실제 로그인/선택/진입 흐름에 중복 검증을 합쳐 실행한다. 배치 중 모든 Assets/Packages/ProjectSettings 쓰기를 멈추고 Editor 조작자는 한 명으로 유지한다. 미실행/통과/실패를 구분하며 배치 항목을 문서 작성만으로 완료 처리하지 않는다.

## 2026-10-19 최신 — 사용자 기능 묶음과 PR

작은 구현 단계·탭·버그 수정·문서·캡처마다 PR을 만들지 않는다. 사용자가 이해할 사용자 기능 흐름이나 게임 화면 묶음을 기준으로 관련 UI·서버/클라이언트 연결·독립 리뷰·배치 검증·공개 사이트 결과를 한 브랜치/한 PR에 담는다. 내부 커밋과 파일 소유권은 분리할 수 있다. 서로 무관한 기능을 크기만 키우려고 섞지는 않는다. 제목·Slack 보고는 큰 결과, 막힌 점의 해결, 최종 검증만 짧게 쓴다. 사용자가 PR을 먼저 올리면 검토·승인한다고 지정했으므로 검토 가능한 검증 묶음의 일반 push/PR 생성은 진행하고 병합·공개는 승인 전까지 기다린다. 되돌리기 어려운 운영·DB 파괴·비밀·권한·비용의 기존 사전 승인과 실행 플랫폼 통제는 유지한다.
