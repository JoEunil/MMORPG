## 서버 리팩토링에서 먼저 정할 접점

### 몬스터 delta 추가 점검

- 서버 dirty X/Y 작성→Broadcast→ClientCore 파싱→ViewModel dispatcher→ObservedWorld의 몬스터별 필드 병합→MotionHistory→매 프레임 Render 경로를 읽었다. 좌표가 delta에서 전혀 반영되지 않거나 Full 때마다 기존 몬스터 보간을 Reset하는 경로는 조사한 코드에서 발견하지 않았다.
- 100ms 간격 표본에75ms 표시 지연을 적용하고 끝표본 이후 hold하면, 계산상 매 주기 약25ms 동안 정지하고 다음 표본 수신 시 이미 지난 보간 구간 일부를 건너뛴다. 보간 코드가 있어도 일정 속도가 유지되지 않는 구조다. 이는 이상적100ms 입력에 대한 코드상 판단이며 사용자 세션의 실제 주원인 확정은 아니다.
- ClientCore ReceiveTick은50ms 주기로 큐를 모아 처리하고 LoginScreen.Update는 작업을 한 번에 소진한다. MotionHistory 시각은 서버 표본 시각/소켓 수신 시각이 아니라 Unity 콜백 처리 때 붙인다. 프레임 지연으로 여러 패킷이 함께 처리되면 원래 시간 간격이 압축되어 보간 속도가 튈 수 있다. 실제 묶음 발생량은 미계측이다.
- ActorMotion은 이 화면 위치의 프레임별 차이로 보행량·stride를 정하므로 위치 hold/점프가 보행에도 전달된다. 수신 파싱 누락과 표시 시간축 문제를 구분해서 후속 계측한다.
- 별도 내구성 위험: DeltaSnapshotMonster는 필드 쓰기 반환값을 검사하지 않고 dirtyBit를 지우며 Broadcast 큐 거절도 호출자에게 돌려주지 않는다. 버퍼/큐 부족이면 delta 손실 후 Full까지 기다릴 수 있다. 현재 플레이에서 이 실패가 발생했다는 근거는 없다.
- 우선 조치는 실제 간격/지터·큐 대기·표본 hold 비율을 함께 확인하고, 그 결과로 표본 시간축과 충분한 보간 버퍼를 맞추는 것이다. AI 변경이나 무조건적인 송신 빈도 증가는 선행 해결책으로 확정하지 않는다. 이번에도 코드 수정·실행 테스트는 하지 않았다.

- **시간과 이동:** 서버 틱과 몬스터 송신 주기를 구분한다. 유저 속도·몬스터 속도·시각 보정 예산을 독립적으로 유지한다. 보간 계측을 위해 표본 시각이 무엇을 뜻하는지 명시한다.
- **스킬 방향:** 월드 좌표의 각도 단위·0축·회전 방향·정규화·NaN/무한대 거절을 정한다. 요청/결과/서버 진행 중 스킬이 같은 고정 각도를 사용한다. 이동 dir 유지+aimAngle 추가와 전체 dir 전환을 비교한 뒤 패킷 길이·필드 순서·DB 영향·동시 배포 범위를 확정한다. 방향키 이동은 통상8방향이므로 float 필드만 추가해도 자유로운360도 조준 입력이 생기는 것은 아니다.
- **아이템 책임:** 수량·지급·영속성은 Cache, 현재 HP/MP·쿨다운은 Zone 캐릭터 상태다. 소비 성공 이후 회복하고 요청 ID·소유권 epoch·늦은 응답 처리를 보존한다. 퀵슬롯은 이 판정을 대체하지 않는다.
- **보상:** 처치 EXP·포션·골드를 한 보상 데이터에서 어떻게 표현할지 정한다. 지급 이벤트의 중복 방지·미로딩/실패·재접속/서버 재시작 중 보장 수준과 확정 알림을 명시한다. 기존 잔액 증가 함수 호출만으로 장애 내구성까지 보장한다고 가정하지 않는다.
- **정본 데이터:** 스킬·몬스터·성장과 같은 서버 정본→Exporter→클라 경로를 활용한다. 맵/스폰은 기존 Unity→서버 경로를 유지한다. 아이템 카탈로그 공유는 아직 추가 작업이며 이미 통일됐다고 기록하지 않는다.

프로토콜은 요청26→30바이트, 결과필드21→25바이트로 동시 적용해야 한다. 서버·ClientCore·Unity·DummyClients를 같은 후보로 빌드한다. 이전 빌드 혼용은 지원 완료로 간주하지 않는다. DB 마이그레이션 없음. 검증 후보 완성 후 직접 영향만 검사하며, 현재 구현 중 결과를 통과로 보고하지 않는다. 경제·아이템 등 후속 묶음은 이번 조준 구현에 무관하게 확대하지 않는다.

자유각도 묶음은 구현·직접자동검사·실서버배치·후속종합검수까지 범위 통과했다. 최신 결과는 history/2026-11-04-free-aim/RESULTS.md, 다음 행동은 HANDOFF를 따른다. 위의 과거 '서버 보류/미구현'은 결정 당시 기록이며 현재 명령이 아니다. MP/등급 포션·골드·구역 레벨 등 후속 범위는 아직 변경안이다.


## 패링·피격·공격 예고 — 제작 중 계획

| 비교안 | 판단 |
| --- | --- |
| 기존 ACTION 예약 슬롯 | 패킷 추가는 적지만 요청 상관성과 거부·남은 쿨다운 응답이 부족하다. |
| 전용 PARRY 요청·응답 + 기존 결과 방송 | **채택.** 입력 요청과 권위 있는 쿨다운 응답을 분리하고 기존 AOI 연출을 재사용한다. |
| SkillData에 방어 스킬 추가 | 고정 슬롯·phase·콘텐츠 검증까지 확장해야 하므로 이번에는 제외한다. |

### 메시지와 상태 수명

- opcode `PARRY=48`, `PARRY_RES=49`를 사용한다. 요청은 `requestID:uint64, ownershipEpoch:uint64` 순서로 본문 16/프레임 24바이트다. 응답은 같은 두 ID, `status:uint8, windowRemainingTicks:uint32, cooldownRemainingTicks:uint32` 순서로 본문 25/프레임 33바이트다. 서버·ClientCore·Unity·DummyClients의 정의·필터·길이를 함께 맞춘다.
- 상태값은 Invalid=0, Accepted=1, Cooldown=2, Dead=3, StaleOwnership=4, StaleRequest=5, Unavailable=6이다. 세션에 최신 요청 ID·epoch·판정 상태를 보관한다. 낮은 ID는 거절하고 정확한 중복은 재발동 없이 현재 남은 틱을 반환한다. 구역·연결 수명과 요청 ID 초기화 규칙을 함께 대조한다.
- 요청은 `FLAG_SIMULATION`으로 Zone 큐에서 처리한다. 기존 틱의 쿨다운 감소 후 요청→피해 판정 순서를 사용하므로 수락한 틱부터 5번의 판정 기회를 갖는다. 서버 `SkillData.h`의 window=5/cooldown=30/charges=1을 단일 정본으로 두고 기존 서버 콘텐츠 exporter의 `parry` 블록으로 공유한다. 새 Manager나 DB 필드는 만들지 않는다.
- 성공적인 구역 이동에서는 window를 0으로 취소하고 확인된 쿨다운은 유지한다. 사망·귀환에서도 window를 지우고 남은 쿨다운을 보존한다. 재접속에서는 기존 일시적 스킬 쿨다운과 같이 초기화하는 정책이며 저장 지속성을 주장하지 않는다. ClientCore는 구역 전환·연결 종료 시 이전 pending을 취소하고 요청 ID·epoch·현재 모델이 맞는 응답만 적용한다.

### 피해·표현의 책임

- 몬스터→플레이어 피해 적용 직전 한 지점에서만 검사한다. **살아 있고 실제 범위 안에 있는 대상에 양수 피해가 들어올 때만** 활성 방어 1회를 즉시 소모한다. 범위 밖·0피해·사망 대상은 소모하지 않는다. 같은 틱의 두 번째 공격은 정상 피해를 주며, 비 AOE 공격의 기존 대상 선택·break 의미를 유지한다.
- `ACTION_RESULT` 예약 표식은 `skillSlot=254, skillID=UINT32_MAX, phase=0 Begin / 1 Success`다. 실제 SkillData 조회 대상으로 쓰지 않는다. 수락 시작과 성공 순간 각각 현재 위치·소속 구역의 기존 AOI 경로로 방송한다. 구역 이동으로 취소된 이전 구역 표현은 전환 정리에서 제거하며 원격 표현은 짧은 시각 효과만 유지한다.
- 직접 응답은 자기 HUD의 수락·거부·남은 쿨다운을, 방송은 자기/원격 방어 모션과 효과만 담당한다. 늦은 ACK나 성공 방송으로 방어창·쿨다운을 다시 활성화하지 않는다. 성공한 공격에는 일반 피격 모션·피해 섬광을 중복 적용하지 않는다. 실패한 방어는 기존 HP 감소·피격 표현을 따른다.
- Space는 텍스트 입력·모달·OS 포커스 가드를 적용하며 키 누름 한 번에 요청 한 번만 보낸다. 마우스 조준을 요구하지 않고, 거부·응답 지연에 자동 재요청하지 않는다.

### 소유권과 최소 확인

서버/프로토콜 담당은 요청·응답·세션 중복 처리·Zone 타이머·피해 훅·결과 방송·서버 데이터/export와 ClientCore 경로를 맡는다. 클라이언트 표현 담당은 콘텐츠 import·Space/HUD·방어/피격·공격 예고·원격 표현을 맡는다. 공유 파일은 담당자 간 먼저 조정하며 사용자 몬스터 AI·경제·스턴 처리는 수정하지 않는다.

### 거래소 수령함 후속 계약 — 읽기 분석, 구현 미승인

현재는 구매 확정 뒤 ‘Receive items’ 버튼으로 배송 복구를 요청한다. `MarketScreen.BuyReceived`는 구매 성공 후 직접 배송을 호출하지 않으며, 서버 구매 처리는 outbox READY 생성까지다. 취소 반환은 서버에서 즉시 배송을 시도한다. 따라서 아래 선택은 기존 구매 결제·판매자 다이아 정산과 구분한다.

| 준비한 방향 | 재사용과 추가 계약 |
| --- | --- |
| 배송 대기 목록 + 일괄 받기 | 기존 outbox·CheckOutbox·DeliverItem·event ring/flush를 유지한다. 조회는 지급 부작용 없는 새 목록 계약이 필요하다. 받기는 현재 최대30건 일괄 배송을 재사용할 수 있다. |
| 항목 선택 수령함 | 위 목록에 requestID/eventID를 지정하는 개별 수령 계약이 더 필요하다. 서버 세션의 캐릭터 소유권을 검사하고 같은 eventID 재요청은 중복 지급하지 않아야 한다. 새 결제·새 지급 이벤트를 만들지 않는다. |

목록 초안의 최소 표시 값은 eventID/itemID/quantity이며, 다음 페이지·구매품/반환품 구분은 실제 필드·정책을 확인한 뒤 정한다. 기존 CheckOutbox 응답은 requestID/status/delivered/duplicated/blocked(전체25바이트)로 ‘목록’이 아니다. 일부 배송 뒤 막힐 수 있으므로 전부 성공/실패로 단순화하지 않는다. 판매 대금 Claim(listingID)은 다이아 정산이며 구매품 수령에 전용하지 않는다.

주의: READY라도 캐시에 이미 지급되고 DB flush/CLAIMED 전일 수 있다. 새 목록에서 이를 무조건 미수령으로 표시하지 말고 기존 applied-event 상태와 조정해야 한다. 현재 ACK를 영속 저장 완료로 강화해 설명하지 않는다. 실DB 적용·장애 복구는 이번 읽기 분석에서 검증하지 않았다. 새 테이블·일반 메일·만료·장비·자동 지급 정책 변경은 승인하지 않았다.

복귀 후 결정할 점은 일괄/개별 수령, 구매품만/반환품 포함 두 가지다. 반환품도 명시 수령으로 통일한다면 현재 취소의 즉시 배송 동작 변경까지 별도로 확인한다. 근거: [거래소 UI](../../UnityClient/Assets/Client/Runtime/UI/MarketScreen.cs), [서버 거래/배송](../../CacheLib/Handler_Bazaar.cpp), [기존 SQL 트랜잭션](../../Resources/DB/procedure.sql), [배송 중복 방지](../../CacheLib/CacheStorageInventory.cpp), [저장 후 outbox 처리](../../CacheLib/CacheFlush.cpp).
