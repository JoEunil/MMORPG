# 작업 실행 흐름

공통 규칙은 [AGENTS.md](../../AGENTS.md), 현재 상태는 [HANDOFF](HANDOFF.md)를 따른다.

## 시작과 계획

Git 정본·작업 트리·Editor 프로젝트·서버/DLL 기준을 실제 도구로 대조한다. 사용자 변경을 보존하고 현재 요청이 지침 정리면 게임 개발을 시작하지 않는다.

관련 진입점 → 호출부 → 상태 소유자 → 계약 → 기존 검증을 필요한 범위만 탐색한다.

| 작업 | 최소 계획 | 확인 |
| --- | --- | --- |
| 문구·배치·문서 | 목표·범위·방법 | 화면·링크·일관성 |
| 기능·수명 버그 | 흐름·실패 경계·담당 파일 | 직접 영향 자동 시나리오 |
| 다중 모듈·패킷 | 의존 순서·호환·소유권·복구 | 관련 빌드·통합 경계 |

필요한 작업 카드는 기존 작업 기록 안에 목표/완료 조건, 기준 소스/수정·제외 파일, 미확인/담당자, 검증/종료 조건만 적는다. 작은 단계마다 새 문서를 만들지 않는다.

## PR 단위 실행

관련 미완료 기능을 먼저 한 사용자 흐름으로 묶고, 해당 범위의 구현을 모두 마친 뒤 통합 리뷰 → 직접 영향 검증 → 공개 자료·인계 → 게시 승인을 한 번에 진행한다. 작은 기능마다 이 절차를 닫거나 사용자에게 재개를 요청하지 않는다. 구현 중 컴파일 차단 등은 즉시 해결할 수 있지만, 이미 통과한 테스트를 묶음 마감이라는 이유로 반복하지 않는다. 관계없는 기능을 PR 크기만 늘리려고 추가하지 않는다.
## 기획·아트 방향 선택

새로운 큰 방향이나 기존 선택과 충돌하는 기획·아트는 `관련 작업 모으기 → 대표 샘플 묶음 → 한 번의 일괄 선택 → 선택 범위 함께 제작 → 통합 검증·결과 피드백`으로 진행한다. 사용자가 전문 용어로 명세를 만들도록 요구하지 않고 Coordinator가 일상적인 요구를 비교 가능한 안으로 바꾼다. 선택 질문은 Coordinator가 한 번에 모아 전달한다.

- 먼저 기존 결정·서버 기능·구현 제약을 확인한다. 이미 고른 방향 안의 문구·간격·색 보정 같은 작은 수정은 자율 진행하며 매번 선택이나 승인을 요청하지 않는다. 본질적인 사용 흐름·미술 방향이 달라질 때만 다시 비교한다. 게시·권한 승인과 취향 선택은 구분한다.
- 기본적으로 관련 작업 3~5개를 하나의 비교 화면에 모은다. 각 작업은 차이가 분명한 저비용 샘플 2개와 추천 조합을 제시하고, 판단 축은 작업마다 1~2개로 제한한다. 실제로 선택할 차이가 없으면 샘플을 억지로 늘리지 않는다. 각 안의 효과·단점·구현 비용과 추천 이유를 짧게 적는다. 한 안만 유난히 정교하게 만들어 선택을 유도하지 않는다. 요소별 조합과 ‘마음에 드는 안 없음’도 허용하며 미응답을 선택으로 간주하지 않는다.
- 기획은 화면 순서·조작 사례로 비교하고 기존 서버에서 가능한 범위를 표시한다. 아트는 같은 카메라·해상도·장면 조건의 비교 화면을 사용한다. 저비용 시안·콘셉트·에디터 예시·실제 게임 화면을 구분하고 고품질 콘셉트가 그대로 구현된다고 약속하지 않는다.
- 선택한 요소·피할 요소·이유(사용자가 말한 경우)·적용 범위·임시/확정 상태를 BRIEF의 해당 기준에 짧게 남긴다. 모르는 이유를 추측하거나 한 화면의 선택을 전체 프로젝트의 영구 취향으로 확대하지 않는다. 후속 요청이 바꾸는 범위를 기록하고 과거 결정은 기존 이력에 보존한다.
- 이미 선택한 방향은 고정 조건으로 표시하고 같은 질문을 반복하지 않는다. 사용자는 묶음 전체나 작업별 조합을 한 번에 고르거나 일부만 보류할 수 있다. 미선택 항목만 대량 제작을 기다리며 선택한 항목과 독립 작업은 진행한다.
- 선택 후 각 대표가 기존 계약·가독성·수명 기준을 만족하는지 Agent가 확인하고 선택한 작업들을 함께 제작한다. 작업 하나가 끝날 때마다 취향 피드백이나 별도 대표 승인으로 멈추지 않는다. 최종 결과·직접 영향 검증·남은 문제도 한 묶음으로 전달한다. 선택 방향에서 크게 벗어나거나 새 계약·비가역 위험이 생긴 항목만 근거와 함께 다시 묻는다.
- 취향 선택과 품질 검증은 별개다. 가독성·조작 방해·서버 범위/판정·성능 제약은 Agent가 점검하고, 선택안과 충돌하면 근거와 가까운 대안을 제시한다. 선택지와 평가가 실제로 있었는지 기록하며 새 절차를 과거 작업의 성과로 소급하지 않는다.

### 선택지 담당의 입력·출력 경로

선택지 담당은 [역할 지침](roles/decision-curator.md)을 따른다. 새로운 서버나 별도 대화 라우터를 만들지 않고 기존 Agent 메시지·비동기 사용자 질문을 사용한다.

현재 묶음을 구현하는 동안 선택지 담당은 다음 1~2개 기능 묶음의 판단 필요점을 미리 확인한다. 기존 결정으로 진행 가능한 항목은 질문 없이 넘기고, 실제 새 판단이 필요한 항목만 같은 조건의 샘플로 묶어 구현 착수 전에 제시한다. 준비 목록은 BRIEF의 선택 상태에 연결하며 `준비 중 / 제시 가능 / 답변 대기 / 선택 완료`를 구분한다. 다음 범위나 제약이 달라질 때만 갱신하고, 근거 없는 먼 미래 기능·반복 질문·상시 대기 실행은 만들지 않는다. 준비를 마치면 슬롯을 반환하고 새 근거나 실제 답변이 생길 때 재활성화한다.

1. 총괄 → 선택지 담당: 묶음/개정, 사용자 목표·확정 조건, 기획/아트 근거·동일 조건의 샘플, 이번에 고를 항목, 영향 파일과 독립 작업을 전달한다.
2. 담당 → 총괄: 보드 링크/파일, 항목별 두 안·장단점·추천 조합, 질문 하나, 답변 형식, 선택이 필요한 작업 목록을 반환하고 실행을 끝낸다.
3. 총괄 → 사용자: request_user_input_async로 묶음 질문을 한 번 게시한다. 보드를 확인할 수 있는 링크를 함께 제공하고 HANDOFF에는 해당 묶음 참조만 남긴다. 도구가 없으면 질문을 한 번 전달하고 미응답 상태를 보존한다. 독립 작업이 있으면 답변 대기 때문에 전체 턴/개발을 끝내지 않는다.
4. 사용자 → 총괄 → 같은 담당: 실제 답변 원문·출처·묶음/개정을 후속 메시지로 전달한다. 담당은 선택/일부 보류/불명확 항목과 적용 범위를 반환한다. 출처가 없거나 개정이 다른 답변은 임의로 매칭하지 않는다.
5. 총괄 → 구현/아트: 검증된 선택을 BRIEF 해당 기준에 한 번 반영하고 선택된 작업만 배정한다. HANDOFF의 대기 항목은 해소한다. 애매한 항목만 추가 확인하며 전체 선택을 다시 묻지 않는다.

선택의 현재 정본은 BRIEF의 '선택 대기와 전달'이며 일반 작업/게시 승인은 HANDOFF·Slack 절차를 따른다. 대기 행은 묶음/개정·보드·질문 참조·고정 조건·선택 항목·상태·답변 근거만 짧게 유지한다. 완료된 실제 선택은 기존 해당 기준에 반영하고 원문/샘플 링크는 이력에 보존한다. 문서와 채팅에 서로 다른 선택 상태를 유지하지 않는다.

현재 Slack 수신기는 승인 명령용이다. 취향 선택을 승인으로 읽거나 문서 추가만으로 Slack 선택 자동 수신·별도 Agent 직통 채팅이 구성됐다고 보고하지 않는다. 새 대화 생성·수신기 프로토콜/고정 대상 변경이 필요하면 실제 도구와 사용자 요청 범위를 별도로 확인한다.

## PR 묶음 기준

작은 조작 개선·검증 기록·지침 보완만으로 새 PR을 만들지 않는다. 기존 PR과 관련된 후속 구현은 그 PR에 누적하고, 다음 게시 시점은 사용자 관점의 주요 흐름을 구현·표현·통합 검증까지 마친 때로 잡는다. 변경 파일 수나 커밋 수를 채우기 위해 무관한 기능을 추가하지 않는다. 현재 PR의 병합 여부와 새 범위 영향을 확인하고, 사용자가 조기 게시를 요청하거나 독립적인 긴급 수정이 필요한 경우만 작은 PR로 분리한다.

## 구현 → 리뷰 → 검증 → 전달

1. 기존 계약·책임 안에서 최소 변경을 구현하고 독립 파일만 병렬 배정한다.
2. 위험 diff를 독립 검토한다. 리뷰 의견도 코드·계약과 대조한다.
3. 후보를 동결해 직접 영향만 배치 검증하며 에셋 쓰기·재임포트를 멈춘다.
4. 제품/fixture/환경/도구 실패를 구분해 영향받은 실패만 재확인한다.
5. 구현·통과·차단·미실행과 복원 상태를 기록하고 바뀐 공개 결과만 갱신한다.
6. 게시가 필요하면 DELIVERY의 최종 승인·통합 절차를 따른다.

늦은 응답·창 닫기·취소·재접속·Zone·종료는 이번 변경에 관련된 경계만 선택한다. 전부 매번 실행하지 않는다. 서버 변경안은 원인·최소 diff·소비자·호환·동시 적용·검증·복구를 포함한다.

HANDOFF에는 현재 목표·미확인·승인/입력 상태·다음 행동만 남긴다. 끝난 카드·리뷰·검증과 운영 기록은 [작업 이력](history/2026-10-24-work-records/README.md)처럼 해당 묶음의 history에 보존하고 링크를 갱신한다. 미완료 관찰을 완료로 바꾸거나 과거 승인을 현재 명령으로 재사용하지 않는다. 계약·역할·기능 문서는 이관 대상과 구분하며 입력 허용은 HANDOFF 한 곳에서 확인한다.

이전 단계표·초기 구축 계획·양식은 [이력](history/2026-10-24-guideline-audit/README.md)에 보존한다.
